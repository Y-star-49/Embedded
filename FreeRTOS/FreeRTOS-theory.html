深入原理版 · 以 FreeRTOS V10.4.6、单核 STM32F103 / Cortex-M3 为主要背景

01 基础知识：任务与调度的整体模型

1.1 为什么需要任务

一个设备可能同时需要采样、通信、显示和记录数据。这些工作对时间的要求不同：显示稍晚一点可能可以接受，采样或控制处理过晚可能破坏系统功能。

裸机也能通过中断和状态机安排这些工作。RTOS 提供的是一种组织方式：把相对独立的执行流程表示为任务，由内核维护它们的运行资格和等待关系，再根据调度规则分配 CPU。

单核系统在同一时刻只能执行一条指令流。多个任务通过切换交替前进，形成并发；它们并没有在同一个 CPU 核上同时执行。

1.2 任务到底是什么

任务包含一条能够暂停、随后继续的执行流程，以及内核管理它所需的信息。理解任务时应同时想到三部分：执行内容、独立任务栈、任务控制块。

任务栈保留函数调用关系、局部数据和被保存的执行现场。任务控制块记录优先级、栈位置和等待状态等。任务函数只是执行内容的入口，同一段任务函数可以被不同任务使用；它们具有各自的栈与控制块，但仍可能访问同一份全局数据。

在这里讨论的普通非 MPU 移植中，任务之间没有天然的内存隔离。某个任务写坏内存，可以破坏其他任务甚至整个内核。

1.3 四种状态如何区分

状态 能否被调度执行 为什么处于这个状态
运行 正在执行 已被选中并获得 CPU
就绪 可以 执行条件已经满足，等待 CPU
阻塞 不可以 在等待时间到达或某个事件成立
挂起 不可以 被显式暂停，需要恢复操作重新获得运行资格

状态变化的主要路径是：就绪 → 运行；运行 → 就绪；运行 → 阻塞 → 就绪；任务被显式挂起后，通过恢复回到就绪。

“从阻塞返回”首先表示恢复运行资格。任务是否立刻执行，还要看优先级、当前中断和调度状态。

从内核结构看，运行任务通常仍保留在对应优先级的就绪列表中，通过“当前任务指针”区分它正在运行。不能把逻辑状态与某一条链表简单地一一对应。

1.4 调度器决定什么

抢占式调度下，调度器选择当前可运行任务中优先级最高的任务。高优先级任务从阻塞转为就绪后，在允许切换的条件下可以抢占低优先级任务。

同优先级任务是否在节拍到来时轮换，由时间片配置决定。协作式调度则主要依赖当前任务主动让出 CPU 或进入阻塞等状态。协作式调度与 FreeRTOS 历史上的 co-routine 功能不是同一个概念。

优先级表达运行次序，不表达工作量。高优先级任务只要一直保持可运行，就可能使低优先级任务长期得不到执行。主动让出 CPU 也不保证低优先级任务能运行，因为让出者仍可能是最高优先级就绪任务。

1.5 “实时”的真正要求

实时性关心的是结果能否在规定时间内完成。平均运行很快，不能证明最坏情况下也满足截止时间。

某个事件从发生到处理完成，可能经历中断响应延迟、任务唤醒、调度等待、资源等待和实际计算。RTOS 提供调度与同步机制，应用仍需控制任务执行时长、临界区长度和资源竞争。

推演检查： 高优先级采样任务阻塞，低优先级显示任务就绪，CPU 应运行谁？

参考判断： 显示任务。调度器只在可运行任务中比较优先级；阻塞中的高优先级任务不参与竞争。

02 系统配置：决定内核行为的规则

2.1 配置文件改变的不只是开关

FreeRTOS 通过编译期配置决定启用哪些机制、为哪些对象预留存储，以及采用哪些行为规则。同一版本内核在不同配置下，可能具有不同的调度方式、时间分辨率和内存占用。

因此，讨论“FreeRTOS 一定会怎样”之前，要先明确处理器移植、调度方式、节拍频率和功能配置。

2.2 应当按什么层次理解配置

配置层次 控制内容 对系统的影响
调度规则 抢占、时间片、优先级数量 哪些情况下发生任务切换
时间基础 Tick 频率、Tick 计数宽度 延时分辨率、计数回绕周期
对象能力 通知、互斥量、定时器等 哪些协作机制可用
存储策略 静态与动态创建、堆容量、栈容量 对象如何获得内存，何时可能失败
中断边界 内核中断优先级、系统调用阈值 哪些 ISR 能访问内核对象
观测能力 断言、栈检查、运行时间统计 能发现什么问题，付出多少开销

常见的 config 类配置决定整体能力，INCLUDE 类配置决定部分可选操作是否编译进去。掌握分类比逐个背宏名更有价值。

2.3 节拍频率的取舍

Tick 是内核的离散时间单位。Tick 周期等于节拍频率的倒数，例如 1000 Hz 对应 1 ms，100 Hz 对应 10 ms。

提高节拍频率通常能细化延时和超时的粒度，但也会增加节拍中断和相关调度处理的频率。它不会自动提高外设的采样精度，也不能消除中断和高优先级任务造成的执行延迟。

微秒级严格时序通常需要依靠硬件定时机制。把 Tick 配得更快，不能代替对整个响应链路的分析。

2.4 优先级数量和任务数量是两回事

系统可以有多个任务共用一个优先级。允许的优先级级数不等于最多能创建多少个任务；任务总数更多受到内存、栈空间和调度负载限制。

在典型实现中，每个优先级对应一条就绪列表。增加优先级级数也会增加部分内核管理数据。优先级应体现响应需求和依赖关系，而不是按模块数量机械分配。

2.5 配置为什么会相互影响

开启软件定时器，会引入定时器服务任务、服务任务栈和命令队列；提高通知数组长度，会增加每个任务控制块的存储需求；扩大堆，并不会自动扩大某个已经创建任务的栈。

动态分配时，RTOS 堆占用 RAM；静态创建时，对象所需的 RAM 也没有消失，只是由应用提前提供。评估内存时应合并考虑所有任务栈、内核对象、全局变量和中断栈。

推演检查： 把 Tick 从 100 Hz 提高到 1000 Hz，某个任务就一定能每隔 1 ms 准时执行吗？

参考判断： 不一定。时间粒度变细了，但实际执行仍取决于优先级、CPU 负载、中断和资源等待。

03 任务创建和删除：执行现场的建立与回收

3.1 创建任务为什么需要栈和控制块

任务必须在被切换出去后记住“执行到哪里、函数调用到了哪一层、局部数据是什么”。任务栈承担其中的大部分存储，任务控制块则为调度器提供找到和管理这个任务的入口。

任务控制块可以理解为内核的管理记录，其中包括栈顶位置、优先级、状态列表项、事件列表项，以及按配置启用的通知和统计信息。任务句柄用于引用这个对象，不等于任务函数的地址，也不是能够永久有效的编号。

3.2 创建过程为什么像准备一次“恢复运行”

新任务虽然尚未执行过，但内核会先构造一份初始执行现场，使后续恢复过程能够把 CPU 带到任务入口。

创建过程可以按因果关系理解：

  1. 准备控制块和任务栈的存储空间。
  2. 记录任务优先级、名称及其他管理信息。
  3. 在栈中构造初始上下文，使第一次恢复后从任务入口开始。
  4. 初始化列表项，将任务加入对应的就绪列表。
  5. 如果调度器已经启动，再根据优先级和调度规则判断是否切换。

因此“创建成功”说明对象和初始现场建立成功，不代表任务已经执行完初始化工作。新任务有时甚至会在创建它的低优先级任务继续向下执行之前开始运行。

3.3 动态与静态创建的本质差别

方面 动态创建 静态创建
存储来源 内核向堆申请 应用预先提供
主要风险 堆不足、碎片、分配耗时 容量估算错误、存储生命周期错误
生命周期管理 删除后按内核规则回收动态存储 应用负责存储的持续有效和后续复用
执行性能 创建完成后按相同调度机制运行 不会仅因静态创建而更快运行

“静态”描述的是存储提供方式，不表示任务永远不能删除。任务删除并完成相关清理后，应用可以在确保不存在旧引用的前提下重新使用其存储。

3.4 任务栈为什么不能只按局部变量大小估算

栈还需要容纳嵌套函数调用、临时保存数据、上下文保存和库函数消耗。最深调用路径不一定出现在平常运行时，错误处理、格式化输出和复杂计算也可能显著增加栈需求。

FreeRTOS 原生接口中的栈深度通常以栈元素计数。在这里的 Cortex-M3 移植上，一个栈元素是 4 字节。这个约定不能直接套到其他封装层。

在本书讨论的移植中，普通任务使用 PSP，异常处理通常使用 MSP。任务栈足够大，不代表中断栈也足够大；发生异常时自动保存的任务现场也需要占用当时的任务栈空间。

3.5 删除任务究竟删除了什么

删除首先撤销任务的调度资格，并将其从有关列表中移除。动态创建对象的控制块和栈，还需要在合适时机归还内存。

任务不能一边使用自己的栈，一边把这段栈交给其他对象。因此，自删除任务的动态存储通常交给空闲任务后续回收；删除其他任务时，V10.4.6 的常见单核路径可以直接进行相应清理。

内核不会替应用自动归还这个任务持有的所有资源。任务自己申请的数据缓冲、持有的互斥量、进行中的外设事务，都需要单独结束或移交。直接删除持锁任务，其他等待者可能永久等不到资源。

推演检查： 一个任务自删除后，系统长期没有机会运行空闲任务，会有什么影响？

参考判断： 任务已经不能继续执行，但待回收的动态控制块与栈可能滞留，反复创建和自删除时会造成可用堆持续下降。

04 任务挂起与恢复：控制运行资格

4.1 挂起与阻塞为何要分开

阻塞表达“等待某个条件”：时间到、数据到、资源可用。条件成立后，内核能够沿着该等待关系让任务重新就绪。

显式挂起表达“暂时不允许这个任务运行”。它没有一个到期后自动恢复的普通等待期限，需要恢复操作解除。挂起不删除任务，栈和控制块仍然保留。

4.2 内核怎样挂起任务

内核找到目标任务，将状态列表项从原列表移除，同时清理相应的事件等待关系，再把状态列表项加入挂起列表。若挂起的就是当前任务，必须安排其他可运行任务接手 CPU。

这解释了一个容易忽视的现象：挂起一个正等待队列的任务，会干预它原来的等待过程。恢复后不能简单假设它会完整续接原先的等待条件；具体等待操作可能重新检查条件或走超时路径，业务需要检查结果。

4.3 恢复为何不是“立即执行”

恢复操作把任务重新放入就绪集合。任务仍然要经过优先级选择，以及必要的上下文切换，才开始继续执行。

显式任务挂起不是嵌套计数锁。对同一任务多次挂起，通常一次恢复就解除显式挂起。后面介绍的调度器挂起具有嵌套计数，两者不能混用同一种理解。

4.4 挂起与恢复为什么容易丢事件

考虑接收完成中断通知处理任务的场景：

  1. 处理任务准备挂起，但还没有真正执行挂起操作。
  2. 接收中断先发生，对这个任务执行恢复。
  3. 此时任务尚未挂起，恢复操作不会保存一张“以后再恢复”的凭据。
  4. 任务随后挂起，之前的接收事件没有留下能唤醒它的记录。

问题根源是恢复操作不锁存事件。通知、信号量或队列可以在任务尚未等待时保存相应的状态、计数或数据，更适合建立事件同步关系。官方关于恢复操作的说明

4.5 挂起列表不完全等于逻辑挂起状态

V10.4.6 在满足配置和操作条件时，会把无限期等待事件的任务放入挂起列表，避免它被普通超时处理唤醒。但这样的任务在逻辑上仍是在等待事件，并不是被用户显式暂停。

判断任务状态，需要结合事件列表、通知等待状态等信息。看到状态列表项位于挂起列表，就断言任务只能被恢复操作唤醒，会导致错误推理。

推演检查： 先发通知、后进入等待，与先恢复、后执行挂起，有什么关键区别？

参考判断： 通知可以留下待处理状态；恢复没有为未来的挂起积累一次解除机会。

05 中断管理：硬件执行与内核规则的边界

5.1 中断不是一种更高优先级的任务

任务切换由 RTOS 维护执行现场和调度规则；异常与中断响应由处理器硬件机制启动。ISR 没有普通任务那样的阻塞等待语义。

ISR 中先完成需要及时处理的硬件操作，再把较长工作交给任务，可以缩短其他中断和任务受到的干扰。这里的“交给任务”是改变任务等待条件，而不是在 ISR 中直接运行那项任务的完整工作。

5.2 两套优先级为何看起来相反

比较对象 数值与紧迫程度的关系 谁解释这个数值
FreeRTOS 任务优先级 数值越大，优先级越高 调度器
Cortex-M 中断优先级 数值越小，紧迫程度越高 NVIC / 异常机制

本书背景下 STM32F103 使用 4 个有效中断优先级位，可表达 16 个等级。这个数量来自具体芯片实现，不是所有 Cortex-M 的统一规定。

优先级分组决定有效位如何划分为抢占优先级和子优先级。抢占部分决定是否能够打断另一中断；子优先级用于相同抢占等级的待处理中断之间选序。本书背景通常将有效位全部用于抢占优先级，以保持内核阈值规则清晰。

5.3 为什么某些高优先级 ISR 不能调用内核

内核更新链表等共享状态时，需要暂时阻止可能同时操作这些状态的 ISR。Cortex-M3 常用 BASEPRI 建立阈值，只屏蔽紧迫程度不高于该阈值的一组可屏蔽中断。

更紧急的中断仍能响应，但正因为它们能打断内核保护区，所以不能再调用会访问这些内核共享状态的操作。

假设使用未左移的逻辑等级表达阈值，阈值为 5，那么通常允许调用中断安全内核操作的是等级 5～15；等级 0～4 更紧急，不能这样调用。边界包含阈值本身。实际配置还需区分库接口使用的逻辑值和硬件寄存器使用的左移编码，不能把二者直接混写。

5.4 中断安全接口为什么不能阻塞

任务发现条件不满足时，可以把自己移到等待列表，并切换到另一个任务。ISR 属于正在处理的异常流程，不具有这套普通任务等待身份。

因此 ISR 对队列或信号量等操作必须立即得到结果：成功、失败，或提交一个延后处理请求。带 FromISR 的操作也不是对所有中断等级都合法，仍受前述优先级阈值约束。

5.5 从中断到任务执行，中间有哪些步骤

外设事件 → 进入 ISR → 更新通信对象或通知状态 → 目标任务变为就绪 → 判断是否需要切换 → 请求 PendSV → 在允许的异常返回路径中切换任务。

这条链路说明，任务被唤醒与 CPU 切到该任务是两个动作。ISR 内把任务变成就绪后，常需要按移植要求请求切换，才能及时运行更高优先级任务。

在常见 Cortex-M3 移植中，PendSV 用于上下文切换，并配置在最低可配置优先级，避免在更紧急的中断工作尚未完成时切换线程。SysTick 负责节拍相关处理，SVC 参与首次任务启动；它们的职责不同。

本章的中断屏蔽和编码边界可对照 FreeRTOS Cortex-M 官方说明。

推演检查： 把串口中断设为最高紧迫等级，就一定能更快唤醒接收任务吗？

参考判断： 不能这样推断。中断本身可能更早响应，但若越过允许访问内核的阈值，就不能直接调用相应内核操作，需要另外设计延后处理路径。

06 临界段保护：维护不可分割的状态变化

6.1 临界区保护的是哪一种正确性

有些操作包含多个步骤，其他执行者如果在中间插入，就会看到不完整状态。例如，把节点加入双向链表时，需要修改前驱、后继和节点自身的链接；只改到一半就被另一个访问者打断，链表可能失去一致性。

临界区要保证的是：与受保护共享状态有关的执行者，不能在这个多步骤变化尚未完成时插入访问。它不是“让某段程序运行得更快”，也不是对所有硬件活动的全局冻结。

6.2 单条读写为什么不等于整个操作原子

即便某次对齐读写在硬件上不可分割，“读取旧值、计算新值、写回结果”仍然可能是多个步骤。两个执行者都根据同一旧值计算，可能使一次更新被覆盖。

同理，分别读取两个独立字段都没有撕裂，也不保证读到的是同一时刻的组合。例如长度已更新而缓冲内容还没有更新，接收者仍会看到逻辑上不一致的数据。

volatile 主要约束编译器对访问的处理，不提供互斥、事件通知、复合操作原子性或所有权。它不能替代共享数据协议。

6.3 Cortex-M3 的 RTOS 临界区如何工作

在这里的移植中，内核通过 BASEPRI 屏蔽达到阈值及以下紧迫程度的中断。SysTick 和 PendSV 位于受屏蔽范围，相关调度和切换因此推迟。

高于阈值的紧急 ISR 仍可能运行；NMI、HardFault 等也不属于普通 BASEPRI 屏蔽的范围。如果这些执行者也修改同一份数据，就不能声称普通 RTOS 临界区已经保护了全部访问。

DMA 是另一类独立访问者。CPU 屏蔽中断，不会自动阻止 DMA 改写内存。需要结合缓冲区交接、传输状态等建立一致性规则。

6.4 为什么要支持嵌套

上层操作可能已经进入临界区，随后调用的底层操作也需要同样的保护。如果底层一退出就完全解除屏蔽，上层尚未完成的共享状态会暴露出来。

任务级临界区使用嵌套关系确保最外层退出才解除相应保护。中断级保护则要按该移植的规则保存并恢复进入前的屏蔽状态，避免错误地降低外层保护强度。成对进入与退出，是保持这个状态机正确的前提。

6.5 为什么临界区必须短

被屏蔽的中断要等临界区退出才能响应，被推迟的调度也会增加任务延迟。临界区越长，系统中依赖这些执行者的工作就等得越久。

特别需要避免在临界区里等待另一个任务或被屏蔽 ISR 完成工作。你一边等待它，一边阻止它取得进展，系统可能无法继续。

长时间屏蔽 SysTick 还可能使多个节拍事件合并为一个待处理状态，普通硬件挂起位并不是无限容量的计数器。不能假设退出临界区后总能逐个补回被错过的所有节拍。

6.6 临界区和互斥量如何选择

机制 主要保护方式 等待期间是否能让其他任务运行 典型用途
临界区 暂时排除一组并发执行者 不应在其中阻塞等待 很短的共享状态更新
互斥量 建立任务之间的资源所有权 竞争失败的任务可以阻塞 任务之间的共享外设或复杂资源访问

互斥量允许系统在等待资源时执行其他任务，但 ISR 不能用它建立普通任务所有权。临界区能保护合适范围的任务与 ISR 共享数据，但代价是中断延迟。

推演检查： 一段数据更新只需要三条语句，是否可以不考虑保护？

参考判断： 语句数量不是判断依据。应看中间状态能否被并发访问、操作是否复合，以及所有访问者是否遵守同一保护规则。

07 调度器挂起与恢复：推迟调度而保留中断响应

7.1 挂起调度器到底停了什么

挂起调度器期间，当前任务继续执行，任务间切换被推迟，中断仍可响应。内核通过嵌套计数记录调度被挂起多少层，只有配对恢复到最外层，才恢复正常调度。

这与挂起某个任务不同：后者撤销一个任务的运行资格，前者暂缓整个任务选择与切换过程。

7.2 中断唤醒任务后，为什么需要待就绪列表

调度器挂起时，某段任务上下文可能正在处理与调度有关的数据结构。此时 ISR 仍可能发送消息，使一个等待任务满足条件。

为了避免立即改动当前不宜并发修改的状态列表，内核可以先把该任务登记到待就绪列表。这里保存的是“这个任务应在恢复后完成就绪处理”的记录。

典型的事件唤醒路径会先把任务从事件等待列表移出，将事件列表项借用于待就绪登记，而状态列表项暂时仍留在原等待列表。恢复调度器时，再统一完成状态列表迁移。

这个过渡状态说明：一次唤醒不是某个状态变量瞬间翻转那么简单，而是受保护的一组结构变化。

7.3 节拍发生了，时间怎么处理

在调度器挂起期间，节拍 ISR 仍可进入。V10.4.6 会累计待处理节拍，而不按平时方式立即完成所有任务超时处理。

恢复到最外层时，内核通常先处理待就绪任务，再补处理挂起期间记录的节拍，更新延时任务和有关调度标记，最后在需要时安排切换。

这与“长时间屏蔽节拍中断”不同：这里中断执行过，内核有机会记录次数；屏蔽中断时，硬件可能只保留一个待处理标志。

7.4 为什么这不是低成本的任意长保护

挂起调度器保留了中断响应，但高优先级任务仍不能及时得到 CPU。ISR 接收到了数据，不等于处理数据的任务已经开始工作。

而且恢复时需要处理积累的任务和节拍，挂起期间积累越多，恢复过程的工作量可能越大。因此不能只测被保护主体的耗时，还要考虑恢复调度所花的时间。

挂起期间不应调用会引起阻塞或任务切换的操作，也不应随意调用其他内核服务，除非明确满足该服务的使用约束。等待自己暂停的调度器去安排另一任务，是逻辑矛盾。

7.5 三种“暂停”的对照

操作 当前任务 其他任务 中断
挂起当前任务 停止参与调度 可接手运行 正常按硬件规则响应
挂起调度器 继续执行 暂时不能通过任务切换接手 仍可响应
进入 RTOS 临界区 继续执行短保护操作 切换被推迟 阈值范围内的中断被屏蔽

推演检查： 用挂起调度器保护任务与串口 ISR 共享的缓冲区，是否充分？

参考判断： 不充分。ISR 仍能打断当前任务并访问该缓冲区，必须另外建立与 ISR 相容的保护或所有权规则。

08 列表和列表项：内核如何组织任务

8.1 内核为什么反复移动列表项

内核需要快速回答“谁已经就绪”“谁最早超时”“谁正在等这个队列”。如果每次都扫描所有任务，处理成本会随总任务数扩大，而且很难高效表达不同的排序需求。

FreeRTOS 把任务按用途放进不同列表：就绪列表按优先级分组，延时列表按唤醒时间排序，队列和信号量的事件等待列表通常按任务优先级排序。

列表是索引结构。把任务移到另一个列表，主要是改变节点链接，而不是复制整个任务或整段任务栈。

8.2 双向环形链表提供了什么

每个列表项记录前后节点，列表包含一个作为边界的哨兵节点。这样插入、删除和循环遍历都能使用统一的结构规则。

已知节点时，移除节点通常只需修改少量链接，成本不随列表长度线性增加；但“按顺序找到插入位置”可能需要遍历。不能因为底层用了链表，就把所有列表操作都理解成固定耗时。

列表项还记录所属列表及其拥有者。通过列表项找到任务控制块，是从“排序记录”回到“被管理对象”的关键一步。

8.3 一个任务为什么需要两个列表项

考虑任务等待队列数据，同时设置最多等待 50 个 Tick。内核需要维护两条独立信息：

  • 按时间组织：到了期限，应结束等待。
  • 按对象组织：队列有数据时，应考虑唤醒这个接收者。

任务的状态列表项记录它在调度状态体系中的位置；事件列表项记录它与等待对象之间的关系。两个列表项属于同一任务控制块，但分别进入不同列表。

当事件先发生，内核移除对象等待关系和超时关系；当超时先发生，也必须移除另一个等待记录，避免任务被重复唤醒。这个“双重登记、单次结束”的思想贯穿队列和信号量。

8.4 列表项的排序值并不总是一种含义

状态列表项在延时列表中通常保存唤醒 Tick。事件列表项在常见有序等待列表中，使用与优先级相关的值建立顺序。

事件组的等待列表则还需要保存等待位及控制信息，通知等待又有自己位于任务控制块中的记录。理解时应先问“这条列表为什么存在”，再解释列表项数值，不要把一个字段永久理解为时间或优先级。

8.5 为什么需要两条延时列表

Tick 计数宽度有限，会从最大值回到零。假设为了说明原理，使用一个只有 8 位的计数器：当前值为 250，任务需要等待 10 个 Tick，目标计数值会回绕到 4。

如果把目标值 4 与尚未回绕的目标值 253 直接按普通大小排列，会误以为 4 更早到期。内核把跨越回绕点的等待放进溢出延时列表，计数回绕时交换两条列表的角色。

这样，同一条活动延时列表中的任务可以继续按正常计数顺序处理，不必在每次比较时都重新猜测这个“小数值”属于哪一轮。

8.6 就绪列表里的轮换是什么

同优先级任务共享一条就绪列表。调度选择可以沿列表游标前进，取得下一个任务，从而实现轮换。

因此，“插到末尾”要结合列表游标和插入规则理解，不一定只是按物理哨兵位置理解。关键是内核维持的遍历顺序，而不是图上谁画在最右边。

推演检查： 一个任务同时在延时列表和队列等待列表里，是否说明它同时处于两个逻辑任务状态？

参考判断： 不是。它处于阻塞状态，同时有时间和对象两个唤醒条件；两条记录服务于不同索引需求。

09 任务调度：从选择任务到恢复执行

9.1 调度决策和上下文切换是两件事

调度决策回答“下一个应运行谁”。上下文切换负责“让 CPU 从当前任务的现场转到被选中任务的现场”。

有时发生了调度检查，但最终仍选中当前任务；有时已经知道需要切换，却因中断或调度挂起暂时不能执行。区分这两个阶段，才能解释唤醒延迟和切换请求。

9.2 启动调度器为什么要创建空闲任务

所有应用任务都可能阻塞，系统仍需要一个确定的执行入口。空闲任务使用最低任务优先级，保证始终存在可调度的基础任务。

它还承担自删除任务的资源回收，并为低功耗处理提供机会。它不是没有价值的空转垃圾任务。让空闲任务完全没有运行机会，可能影响清理和功耗，即使应用暂时看起来仍在工作。

启动阶段还会按配置创建定时器服务任务，准备节拍和移植相关硬件状态，然后进入第一个任务。STM32F103 的 Cortex-M3 没有硬件 FPU，不能把其他内核移植里的浮点上下文初始化过程直接搬过来解释它。

9.3 第一个任务为何能“恢复”一个从未运行的现场

第 03 章说明，任务创建时已准备初始栈帧。首次启动时，移植层利用这份预先构造的现场，把寄存器恢复到“即将进入任务入口”的状态。

在常见 Cortex-M3 移植中，启动过程设置 MSP 等启动环境，通过 SVC 路径恢复首个任务上下文，并返回线程模式。此后普通任务切换主要交给 PendSV。

这个设计使首次启动与后续恢复复用相近的上下文布局，减少了“新任务”和“被暂停任务”在恢复机制上的差别。

9.4 一次任务切换如何完成

以任务 A 切换到任务 B 为例，可以分成五个阶段：

  1. 处理器进入异常，自动保存一部分寄存器现场。
  2. 移植层补充保存其余需要保留的任务寄存器，把任务 A 的栈位置记入控制块。
  3. 调度器从就绪集合中选择任务 B，更新当前任务指针。
  4. 移植层从 B 的栈中恢复软件保存的寄存器，并设置 B 的任务栈位置。
  5. 异常返回时，硬件继续恢复其余现场，CPU 从 B 被暂停的位置继续执行。

在 Cortex-M3 的基本异常栈帧中，硬件保存 R0～R3、R12、LR、PC 和 xPSR；常见 FreeRTOS 切换路径补充保存 R4～R11。这里只需理解“硬件保存一部分，软件补齐另一部分”，不必背汇编指令。

切换不需要复制任务的整个栈，也不会重新执行任务入口。局部变量和调用链仍留在各自栈中，恢复正确的栈位置和寄存器，就能继续原来的流程。

9.5 MSP 与 PSP 怎样配合

本书背景下，正常任务线程使用 PSP，异常处理使用 MSP。任务被异常打断时，硬件根据被打断上下文使用的栈保存现场，然后异常处理过程使用 MSP；退出时再按异常返回信息恢复目标线程。

所以“在 PendSV 中操作任务现场”不意味着处理器此时使用 PSP 执行所有异常代码。异常代码可以通过保存的地址访问任务栈，而自身仍在异常执行环境中运行。

9.6 谁触发调度

节拍到来可能使延时任务到期，或者触发同优先级轮换；任务主动阻塞、挂起或删除自己，也需要重新选择；通信操作使更高优先级任务就绪时，同样可能请求切换。

因此，任务切换并不只发生在 Tick 边界。事件驱动系统中，ISR 唤醒高优先级处理任务，通常应争取在中断退出后尽快执行，而不是人为等到下一次节拍。

推演检查： 任务被切换出去十次，它的任务函数就会从入口重新执行十次吗？

参考判断： 不会。恢复执行现场后，继续原来被打断的位置；重新创建任务才会建立新的入口执行流程。

10 时间片轮询：同优先级任务如何轮换

10.1 时间片解决哪一层竞争

优先级先决定哪些任务具有最高运行资格。在这个优先级内部，如果存在多个就绪任务，时间片提供周期性的轮换机会。

所以时间片并不会让低优先级任务按比例分享高优先级任务的 CPU。若一个更高优先级任务持续就绪，低优先级的轮询组依然可能长期不运行。

10.2 为什么“一片等于一个 Tick”容易被误解

默认时间片机制通常在每次 Tick 到来时检查最高就绪优先级是否有多个任务，并在需要时安排轮换。Tick 是全局时间边界，不是为每个新获得 CPU 的任务重新启动的专属倒计时。

假设 Tick 边界为 0、1、2 ms。任务 B 因任务 A 在 0.8 ms 阻塞而开始执行，此时另一个同优先级任务 C 仍然就绪，那么下一个轮换检查仍可能出现在 1 ms，随后可以轮到 C。B 这一次在下个边界前只有约 0.2 ms，不保证获得完整 1 ms。如果只剩 B 一个任务处于该优先级的就绪列表中，则没有仅因时间片到来而切给同级伙伴的必要。

中断执行还会占用墙钟时间。因此“配置了时间片”不能推出同优先级任务获得严格相等的实际 CPU 时间。

10.3 阻塞时为什么不用等本片结束

任务进入阻塞说明它暂时不具备继续执行的条件。继续把 CPU 留给它没有意义，调度器可以立即选择其他就绪任务。

FreeRTOS 常见时间片机制也不会为一个阻塞任务保存“尚未消费的时间额度”，供它以后补用。它维护的是就绪任务的轮换规则，而不是每个任务的个人 CPU 余额。

10.4 关闭时间片会发生什么

关闭时间片后，Tick 不再仅因为同优先级有多个就绪任务就强制轮换。但任务阻塞、主动让出 CPU、优先级变化及其他调度事件仍可能导致不同任务执行。

因此，关闭时间片不等于关闭抢占，也不等于保证某个同优先级任务永远不会被换出。抢占和时间片是两个独立的配置维度。

10.5 时间片为什么不能当同步机制

两个任务哪怕同优先级、看起来交替运行，也不能靠“你这一片写完、我下一片读取”保证共享数据正确。ISR、阻塞、临界区和其他任务都可能改变实际交错次序。

任务间的数据一致性应来自队列、互斥、通知或明确的共享数据协议。调度顺序只决定执行机会，不自动建立数据所有权和完成条件。

推演检查： 两个同优先级任务轮流打印信息，输出看起来交替，能证明它们各获得一半 CPU 时间吗？

参考判断： 不能。打印本身可能阻塞，任务计算量不同，中断也可能介入；输出次序与 CPU 占比不是同一种观测。

11 任务观测：状态、优先级、栈与运行时间

11.1 为什么需要观察任务，而不能只看输出

一个任务没有打印，可能是没有被调度、正在等数据、卡在互斥量上、栈受损，也可能只是输出通道被占用。外部现象通常不足以唯一确定原因。

任务观测的价值在于把这些可能性拆开。先判断运行资格，再看等待对象和资源，最后分析执行时长与内存，通常比直接猜测任务优先级更有效。

11.2 任务状态为什么只是一个快照

读取状态后，ISR 或调度器随时可能改变该任务状态。观察到“就绪”，不能保证下一条指令执行时它仍然就绪；观察到“阻塞”，也不能单独判断它在等待什么。

状态查询适合诊断，不适合用“先查询、再操作”的方式代替同步。例如，先看某任务未运行，再修改它的数据，查询与修改之间仍然可能发生调度。

11.3 基础优先级与当前优先级

基础优先级是任务正常设定的等级，当前有效优先级可能因互斥量的优先级继承而暂时升高。观察到任务实际优先级高于预期，不一定是被错误修改，也可能反映资源依赖。

改变优先级会影响就绪列表归属和调度次序。用提升优先级掩盖等待问题，可能只把饥饿转移到其他任务，不能自动消除死锁或不合理的资源持有时间。

11.4 栈高水位到底表示什么

栈高水位通常表示任务栈自创建以来观测到的最小未使用余量。内核常通过预填充的标记值估计哪些栈区域曾被使用。

它不是“此刻所有可用栈空间”的精确实时度量，也不是已经证明最坏路径安全。测试尚未覆盖的调用路径可能更深；某些栈空间即使被保留但没有实际改写，也会影响标记扫描方法的解释。

原生接口的余量通常按栈元素给出，在本书 Cortex-M3 背景下需乘以 4 才得到字节。任务栈余量、MSP 中断栈余量和堆剩余容量必须分别看。

11.5 运行时间统计记录了什么

内核利用独立计数时基，在任务切换等位置累计任务占用的运行区间。时基比 Tick 更细，可以减少短任务测量时的量化误差。

任务处于阻塞状态的等待时间通常不会作为它的任务运行时间累计。不过，在常见切换点计时方式下，中断耗时可能被归入被打断任务所在的计时区间，不能未经分析就把统计值当成纯粹的业务指令执行时间。

统计比例还依赖采样窗口、计数器回绕和统计起点。启动阶段累计的平均值，可能掩盖最近一秒的突发负载；调试打印和统计格式化也会扰动系统。

11.6 常见现象该怎样推理

现象 值得核查的原因
低优先级任务长期就绪却不运行 更高优先级任务持续就绪，或调度被长时间挂起
多个任务等待同一资源 持有者是否运行、是否被暂停、是否存在循环等待
栈余量不断逼近下限 调用深度、局部大对象、异常路径、库函数开销

推演检查： CPU 平均占用只有 20%，是否能说明系统一定满足实时要求？

参考判断： 不能。短时间突发干扰、长临界区或共享资源阻塞，都可能使某次关键响应超过期限，即使长期平均负载不高。

12 时间管理：延时、周期与超时

12.1 内核看到的时间是离散计数

Tick 计数提供内核时间基础。延时和许多等待期限以 Tick 表达，因此它们天然存在量化边界。

在正常节拍处理且不计额外调度延迟时，等待 N 个 Tick，从调用时刻到目标 Tick 的物理时间通常介于约 N−1 与 N 个 Tick 周期之间，取决于调用发生在当前节拍的哪个位置。到了目标时刻后，任务还可能等待 CPU。

因此，等待 1 个 Tick 不等于保证至少经过一个完整 Tick 周期。需要“不得早于某个物理时间”时，必须考虑量化方式和测量基准。

12.2 相对延时为什么会累积漂移

相对延时以当前调用时刻附近的 Tick 值作为基准。若一轮工作先运行 3 ms，再等待约 10 ms，那么两轮开始时间的间隔通常包含这 3 ms 工作时间和延时，还可能叠加调度等待。

每轮工作耗时变化，下一轮的相位也随之改变。这种方式适合“做完后休息一会儿”，不适合直接表达严格固定的开始时间序列。

12.3 绝对周期等待怎样避免普通累计漂移

周期等待维护一个计划时间轴，例如计划在 0、10、20、30 ms 开始各轮。每次目标从上一计划目标继续增加固定周期，而不是从这次工作结束重新计时。

这样，工作耗时的普通波动不会不断平移整个计划时间轴。但实际开始仍可能晚于计划，因为周期等待只控制最早恢复运行资格的时间，不提供 CPU 预留。

如果一次处理拖到 25 ms 才去等待原计划的 20 ms，目标已经过去，就可能不再阻塞。后续可能连续运行以追赶计划，也可能继续错过期限。应用需要明确超期策略：追赶、跳过、记录告警或重新建立时间基准。

12.4 延时任务是如何被唤醒的

当前任务计算目标 Tick → 从就绪列表移出 → 按目标时间插入延时列表 → 其他任务运行 → 节拍推进 → 到期节点移出延时列表 → 加回就绪列表 → 按优先级获得 CPU。

因为延时列表有序，内核可以从最早目标开始处理到期任务，而不必每个 Tick 扫描所有阻塞任务。若同一个 Tick 有很多任务到期，这次节拍处理仍会产生较多工作。

涉及回绕的等待使用两条延时列表管理，具体原因见第 08 章。

12.5 超时是业务规则的一部分

等待数据时，期限主要限制任务因条件不满足而保持阻塞的时间。期限到了，任务获得重新参与调度的机会，并不保证它立即取得 CPU、完成检查并从等待操作返回。因此，函数实际返回的墙钟时刻可能晚于设置的期限；超时参数不是整次调用的硬截止时间保证。

若任务中途被唤醒，却发现条件又被其他执行者改变，内核需要根据已经流逝的时间计算剩余等待，不能每次重新赠送一整段期限。

具体操作还会在恢复和超时处理时重新检查条件。例如队列接收恢复执行时发现已有数据，仍可能成功接收。不能仅凭外部测得的调用持续时间超过设定等待量，就认定结果必然是超时失败。

零等待表示立即尝试，条件不满足就返回，不是“等一个非常短的 Tick”。无限等待也有条件：portMAX_DELAY 在支持相应配置、且该等待路径允许无限阻塞时才具有无限等待语义，不能把所有传入最大 Tick 值的操作都理解成永不超时。

特别是普通相对延时，不应被当成可靠的无限事件等待方式。它没有表达业务事件本身，也不能替代同步机制。

12.6 忙等和阻塞等待的区别

忙等让任务不断检查条件，期间仍保持可运行并消耗 CPU；阻塞等待把“什么时候恢复运行”的条件交给内核维护，使 CPU 可以执行其他任务或进入空闲。

高优先级任务忙等一个需要低优先级任务产生的结果，可能让结果永远无法产生。阻塞的价值不仅是省 CPU，也是允许依赖链中的其他执行者取得进展。

推演检查： 周期设为 10 ms，而每轮计算最坏需要 12 ms，采用绝对周期等待就能稳定 100 Hz 吗？

参考判断： 不能。单次计算已经超过周期预算，周期等待无法制造额外计算能力，还可能出现持续不阻塞的超期循环。

13 消息队列：数据传递与等待机制

13.1 队列比一个全局变量多了什么

队列保存有限个固定大小的数据项，维护发送和接收位置，并提供多执行者访问时的内部保护、满与空的判断，以及阻塞等待关系。

全局变量可以承载共享数据，但“何时可读、谁能修改、连续消息会不会覆盖、接收方如何等待”都需要另行设计。队列把这些问题中的一部分纳入统一机制。

队列按创建时确定的字节大小复制项目，并不理解应用层的数据类型语义。一个项目可以是带类型标识的统一消息，也可以是指针；不能据此认为传递不同业务消息就必须使用队列集。

13.2 按值复制和传递指针有什么区别

按值复制时，发送成功后队列拥有一份数据副本，发送方随后改动原变量通常不影响这份副本。较大的项目会增加复制耗时和存储需求，ISR 中的大量复制尤其值得关注。

指针项目复制的是地址本身，地址指向的数据不会自动复制。发送成功只证明这个地址进入队列，不证明底层数据会一直有效或不会被修改。

例如，把指向可复用接收缓冲区的地址发出后，DMA 立即开始覆盖同一缓冲，接收任务可能读到后续帧或半更新内容。解决问题需要明确缓冲区所有权、何时允许复用，以及由谁最终归还存储。

13.3 队列内部需要哪些记录

记录 作用
存储区、读写位置 维护数据项的存取
容量、项目大小、当前数量 判断空、满和复制范围
等待发送列表 保存因队列满而阻塞的任务
等待接收列表 保存因队列空而阻塞的任务
内部锁定记录 在特定保护阶段推迟对等待列表的更新

内核保护的是一次队列操作及其相关状态变化。先读取队列数量、再决定发送，是两个独立操作；中间仍可能被其他执行者改变，不能把数量查询当成下一次操作必然成功的承诺。

13.4 空队列上的接收如何建立等待

接收任务发现队列为空，而它允许等待时，需要完成“确认条件、登记等待、退出就绪集合”这一串操作。

最关键的竞争窗口是：任务刚判断队列为空，ISR 就送来数据，而任务还没来得及登记自己正在等待。如果只做简单的先检查后睡眠，就可能数据已到、任务却继续睡着。

内核通过短临界区、挂起调度器、队列锁定记录，以及在适当位置重新检查条件等机制，把等待建立和事件发生协调起来。队列锁定期间，ISR 仍可能改变队列的数据状态，但对事件等待列表的处理可以延后登记，解锁后再完成相应唤醒。

这里的内部“队列锁”不是应用拥有的互斥量，也不是锁住后所有读写都不能进行。它主要用于协调特定阶段的数据变化与等待列表更新。

13.5 数据到来后到底唤醒谁

通常先从等待接收列表选择最高优先级等待任务；在等待优先级未变化等常见条件下，同优先级按等待顺序处理。发送方因满队列阻塞时，也存在对应的等待发送顺序。

数据项的先后顺序与等待任务的选择顺序是两条不同规则。普通尾部发送形成 FIFO 数据次序，不意味着所有接收任务一律按到达先后得到数据。

唤醒某个接收者通常不会把队列里的那份数据永久预留给它。它真正恢复执行并完成接收前，其他允许执行的任务仍可能改变队列，所以恢复后的操作需要再次确认条件。

13.6 满队列说明了什么

队列吸收生产和消费速率的短期差异。如果生产速度长期大于消费速度，有限容量最终都会满。扩大容量可以容纳更长突发，但不能解决长期吞吐不足。

容量选择还会影响消息排队延迟。需要保留每条记录、只关心最新值、允许丢弃旧消息，这三种业务目标对应不同策略。长度为 1 的覆盖队列适合表达最新状态，不能当成可靠保存所有事件的通用队列。

推演检查： 队列发送成功后，是否说明接收任务已处理完这条消息？

参考判断： 没有。通常只说明入队成功。若发送方需要知道处理完成，还要建立独立的完成确认关系。

14 信号量与互斥量：同步、资源计数和所有权

14.1 先分清两个问题

同步关心某件事有没有发生、某个阶段能不能继续。例如采集完成后才允许处理。

互斥关心同一时刻谁有权访问资源。例如多个任务共用一个通信外设时，谁能从事务开始一直使用到结束。

两者有时都表现为“等一下”，但等待的含义不同。选型应先确认业务需要的是事件记录还是资源所有权。

14.2 二值信号量为什么可以保存一次事件

二值信号量只有不可用和可用两种计数状态。释放使其可用，获取成功后消耗这次可用状态。若事件先发生，任务后等待，信号量仍可以保存这一次机会。

它不累计任意次数：当已经可用时再次释放，不会变成两个待处理事件。连续多次事件可能合并，额外释放也可能失败。适用于“有事需要处理”的场景，不一定适用于“每次事件都必须单独计数”。

V10.4.6 常用的现代二值信号量创建方式初始为空；不要把某些旧式创建宏的初始可用行为推广到所有创建方式。

14.3 计数信号量的两种含义

计数信号量有当前计数和最大计数。其队列实现模型是数据项大小为零、容量由最大计数决定；不是固定长度为 1 的队列。

场景 计数表示什么 常见初始含义
事件计数 尚未被消费的事件数量 从 0 开始等待新事件
资源池 当前空闲资源数量 从初始可用资源数开始

计数只表达数量，不保存每次事件的参数、来源和时间戳。若需要这些信息，应同时设计数据存储，或直接使用队列。

释放和获取也不是数学上的无限增减。计数有上限；用通知计数或信号量计数描述高速事件时，都需要分析消费速度和容量边界。

14.4 优先级反转如何形成

设 H、M、L 分别为高、中、低优先级任务，L 持有 H 需要的资源。

  1. L 获得资源，开始处理。
  2. H 就绪并抢占 L，随后因资源被占而阻塞。
  3. M 就绪，因为它高于 L，所以先于 L 执行。
  4. L 不能及时运行并归还资源，H 因此间接等待与该资源无关的 M。

H 等待 L 完成必要资源操作，本身可能无法避免。优先级反转的问题在于，中间优先级工作进一步延长了这段高优先级等待。

14.5 互斥量如何缩短这条等待链

互斥量记录持有者，并提供优先级继承。当 H 因 L 持有的互斥量而阻塞，L 可以临时提升有效优先级，从而减少 M 对 L 的抢占，让 L 尽快完成资源操作。

L 仍需要真实地完成操作并释放资源，H 才有机会继续。继承没有让资源同时属于两个人，也不会把 L 的剩余工作瞬间完成。

互斥量应由取得它的任务释放。ISR 不具有这种普通任务所有权，也无法像任务一样等待，因此不能使用普通互斥量来获取或归还资源。官方互斥量说明

14.6 V10.4.6 的继承为什么不能理解为完美方案

FreeRTOS 使用简化优先级继承。任务同时持有多个互斥量时，释放其中一个通常不会立刻重新计算所有依赖关系并降低到理论上最精确的优先级；正常释放路径要等持有数量降到零才恢复基础优先级。

等待者超时时，V10.4.6 还存在专门的降级处理，在持有者只持有一个互斥量等条件下，可根据剩余等待者与基础优先级调整。不能简单说“只要等待者超时，持有者就一定立即恢复”，也不能说“任何情况下都只能等释放后调整”。

继承不消除死锁，不提供完整的资源访问上限，也不保证复杂多锁依赖中的全部期望顺序。保持持锁时间短、避免无必要嵌套、统一获取顺序，比单纯依赖继承更根本。

14.7 死锁、饥饿和反转有什么区别

死锁是相互等待使相关任务都无法推进，例如 A 持锁甲等锁乙，B 持锁乙等锁甲。饥饿是某任务长期得不到运行机会或资源，但其他执行者仍在推进。优先级反转描述高优先级任务受到较低优先级资源依赖及中间任务干扰。

递归互斥量允许同一持有者多次获取，并要求对应次数释放。它能支持同一资源的分层调用，却不能解决两个任务按相反顺序申请不同锁所造成的死锁。

推演检查： H 等待 L 持有的互斥量，L 正在阻塞等待一个很慢的外设。给 L 继承高优先级，H 就能马上继续吗？

参考判断： 不能。继承改变 CPU 竞争优先级，不会使外设完成，也不会让处于阻塞状态的 L 自动变成可运行。

15 队列集：同时等待多个对象

15.1 它解决的是等待入口问题

一个任务可能既要接收队列 A 的数据，也要等待信号量 B。如果先无限等待 A，那么 B 即使可用，任务也无法及时处理它；反复轮询两者，又需要自行安排检查周期。

队列集把多个队列或信号量的可读、可获取事件汇总到一个等待入口。任务在集合上等待，得到有事件的成员身份，再对那个成员执行实际接收或获取。

不同成员可以承载不同大小的数据，但“数据类型不同”不是必须使用队列集的理由。统一消息队列加类型标识、通知等方法，也可以组织多来源业务。

15.2 集合里保存什么

队列集内部维护事件记录，记录指向发生事件的成员。真实消息仍保存在成员队列中，信号量计数仍保存在成员对象中。

可以把它理解为“哪一个容器值得读取”的通知队列，但不是每个成员只有一个永久槽位。同一成员存在多个可消费项目时，可以对应多条事件记录。

因此，选中成员只是得到操作目标，不等于已经把成员中的消息取出来。

15.3 为什么容量不是成员数量

若成员包括长度为 3 的队列、长度为 5 的队列和一个二值信号量，若要覆盖它们全部可能同时积累的可用项目，集合容量应按 3 + 5 + 1，即 9 来考虑，而不是按 3 个成员考虑。

计数信号量应按其最大计数考虑最坏记录需求。计数上限很大时，集合的额外存储可能变得明显。

这个容量模型适用于遵守队列集使用协议的情况；添加成员时应确保其没有尚未登记的可用项目，否则原有状态不一定自动补齐为集合事件。

15.4 为什么不能绕过集合随便读取成员

集合中的事件记录与成员中的可消费项目需要保持对应。如果某任务没有先从集合选中成员，就直接读取了成员队列，集合里可能还留着一条过时记录。后续等待者取到这个记录，却发现成员已经没有数据。

因此，使用队列集时，应遵守先选择成员、再消费该成员的协议，并避免旁路消费者破坏关系。移除成员也需要满足没有有效项目等约束。

15.5 队列集不能继承普通互斥等待的全部语义

等待包含互斥量的队列集，并不等同于直接阻塞获取该互斥量。内核没有沿这条集合等待关系建立相同的优先级继承行为，因此不能假设集合里的低优先级锁持有者会自动继承集合等待者的优先级。官方队列集约束

队列集还增加了对象与事件记录的维护成本。它适合确实需要同时等待现有多个对象的设计；在重新设计消息流时，也应比较一个统一消息入口是否更清晰。

推演检查： 从队列集得到队列 A 后，还需要真正接收 A 的数据吗？

参考判断： 需要。集合传递的是成员身份与事件记录，业务数据仍在 A 中。

16 事件标志组：用条件组合组织协作

16.1 事件位表达的是状态，不是消息队列

一个事件位可以表示“连接已建立”“采样已完成”或“收到停止请求”。多个事件位组成事件组，任务可以等待指定条件中的任意一个成立，或者全部成立。

事件位本身不保存时间顺序、发生次数或附加数据。某一位已为 1 时再次置 1，仍然只是 1。因此它适合条件组合，不适合单独承担“每次脉冲都要记录”的事件流。

16.2 为什么不是所有位都给用户使用

在 V10.4.6 中，事件位类型与 Tick 类型相关。16 位配置通常可用 8 个应用事件位，32 位配置通常可用 24 个，其余高位用于内核控制信息。

这些控制信息帮助内核表达等待全部还是任意、解除等待后是否清位，以及任务为什么被解除等待。可用位数是版本与配置约束，不应把其他版本或 Tick 宽度的结论直接套过来。

16.3 等待“全部”是什么意思

假设启动任务需要“传感器就绪”和“通信就绪”都成立。两个事件可以在不同时间发生，只要相应位被保留，后来检查时都为 1，就可以满足全部条件。

这不意味着两个动作必须在同一瞬间完成，也不代表两个结果属于同一业务轮次。如果上一轮的位没有正确清理，下一轮可能错误复用旧状态。

因此，要先决定事件位表达持续状态还是一次性完成，并设计每轮开始、结束时由谁清理。

16.4 一次置位为什么可能唤醒多个任务

事件组需要遍历当前等待者，把新的位组合与各任务条件比较。多个等待条件可以同时满足，因此一次置位可能让多个任务就绪。

V10.4.6 的置位处理会先判断相应等待者并登记需要清除的位，再在这一轮处理末尾统一清位。因此，某个等待者请求自动清位，并不意味着同一次置位处理中其他已经等待且条件满足的任务必然看不到该事件。

这与“给一次信号量通常只提供一次可消耗机会”有明显区别。另一方面，后来才开始等待的任务会看到清理后的事件组状态，不保证收到之前那次事件。

等待返回的位值也应理解为与本次解除等待相关的观察结果。由于后续并发访问，返回时全局事件组的当前值可能已经变化。

16.5 为什么 ISR 置位需要延后执行

唤醒多少任务，取决于有多少等待者以及它们的条件。若直接在 ISR 中完整遍历并处理，ISR 时长会随等待者数量变化。

FreeRTOS 的事件组 ISR 置位操作将请求提交给定时器服务任务，再由该任务完成置位与唤醒处理。这缩短了 ISR 中的工作范围，但引入命令队列容量、服务任务优先级和服务延迟等因素。

所以提交成功不等于所有事件等待者已经立即就绪；命令队列已满时，提交还可能失败。即使业务不使用软件定时器，也可能因为这一延后处理路径依赖定时器服务机制。官方维护者对该路径的解释

16.6 同步屏障为什么要合并置位与等待

多个任务要先各自完成准备，再一起进入下一阶段，可以让每个任务设置自己的到达位，并等待所有参与者的位。

如果把“宣告自己到达”和“开始等待大家到达”简单拆为两个独立业务动作，其他任务可能在中间完成检查并清理位，造成竞态。专门的同步操作将相关步骤协调起来，但应用仍需保证每轮参与者一致、没有任务漏报或跨轮重复报到。

推演检查： 同一事件位在接收任务处理前被置位 100 次，任务能从这个位还原 100 次事件吗？

参考判断： 不能。事件位没有次数信息，重复置位会合并；需要计数或队列等机制保存额外信息。

17 任务通知：直接作用于任务的通信机制

17.1 为什么通知可以更轻量

队列、信号量和事件组通常有独立对象。发送者操作对象，再由对象的等待关系找到任务。任务通知把所需的通知记录放在接收任务控制块中，发送者可以直接指定目标任务。

省去独立通信对象及部分间接管理后，很多单接收者场景能减少内存和处理开销。但性能优势不等于语义完全等价，替换前必须确认需要保留哪些信息。

17.2 V10.4.6 支持通知数组

从 V10.4.0 起，一个任务可以拥有多个通知项，每项包含一个 32 位通知值和对应通知状态；数组长度可配置，默认通常为 1。旧的非索引通知操作使用索引 0。

多个通知项可以承载不同用途，但一个任务在同一时刻只能阻塞等待其中一个通知项。向其他索引发送通知，并不会自动唤醒正在等待另一个索引的任务。

因此，通知数组不等于“可同时等待任意索引”的事件汇聚器，也不是自动具有先进先出次序的消息缓存。官方通知数组说明

17.3 通知值和通知状态为何必须分开

通知值承载数量、位或某个 32 位数值。通知状态表达是否正在等待、是否已有通知到达等信息。

对按到达状态接收的通用通知等待，数值为零也可以是有效消息，发送者也可以只发事件而不改变数值。内核中独立的状态记录，让“收到一个值为零的通知”仍可被识别。

计数式通知接收采用另一种条件：检查通知计数是否非零，并按规则清空或减一。如果发送方只改变到达状态而没有增加计数，就不能把它当成成功提供了一次可消耗计数。发送语义与接收语义必须配套，不能笼统地认为所有接收方式都只看到达状态。

17.4 不同更新方式对应不同业务含义

更新方式 可以表达什么 主要边界
只改变到达状态 有事情需要处理 不额外保存次数或数据
计数增加 有多少次尚待处理的通知 计数宽度有限，消费方式需明确
指定位合并 哪些类别的事件发生过 同一位的重复事件会合并
覆盖数值 最新一个状态或结果 旧的未处理值可能丢失
不覆盖未处理值 单槽消息交接 槽位已有待处理通知时发送可失败

接收计数时可以选择一次清空，或者只消耗一个计数，两者对应“合并处理一批工作”与“逐次消费”的不同业务语义。

按位通知可以表达事件集合，但普通通知等待并不自动提供事件组那种任意复杂的“等待全部指定条件”语义。需要由接收任务维护累积状态并进行明确判断。

17.5 通知怎样避免先发生后等待的丢失

发送时，内核在受保护的操作中更新目标通知值与状态。如果目标正等待对应通知，则结束等待并使其就绪；如果目标尚未等待，则保留待处理状态，使后续接收能够识别。

这就是它比单纯恢复任务更适合 ISR 到任务同步的原因：它不仅改变运行资格，还记录了事件已经发生。

不过，清除通知状态、清除位、覆盖值都是会改变这份记录的操作。用同一个通知项承担多个互不协调的业务来源，仍可能相互清除或覆盖。

17.6 哪些事情不适合直接通知

接收者必须是指定任务，不能把 ISR 当接收任务；单个通知项不会像队列一样保存任意长度的多条消息；发送者不能阻塞等待通知槽空出来；一次通知也不会自动广播给多个接收任务。

把队列替换为通知时，尤其要检查消息数量、数据宽度、发送方等待和多接收者需求。数据还存放在共享缓冲区时，通知只表明条件变化，缓冲区所有权仍需另外设计。

推演检查： 给任务建立四个通知索引，是否就能让它一次等待这四个来源中任意一个到来？

参考判断： 不能。任务一次只能阻塞等待一个索引；若要汇聚多个来源，需要让来源更新共同等待项，或使用适合多条件等待的其他机制。

18 软件定时器：共享服务任务中的定时处理

18.1 软件定时器与硬件定时器的区别

软件定时器保存一个计划到期时间，到期后由内核服务机制调用回调。它复用内核时间基础和一个服务任务，不需要为每个定时器分配独立硬件定时模块或独立任务。

硬件定时器则由外设计数、比较等机制产生硬件事件；其输出或中断响应链路与软件定时器不同。软件定时器适合超时管理和周期性服务，不提供硬件级精确输出时序的保证。

18.2 为什么一个服务任务能管理许多定时器

每个定时器对象保存周期、自动重装属性、回调入口及列表记录。服务任务根据最早到期定时器确定下一次等待期限，同时等待命令队列中的新请求。

等待可以因为“有新命令”提前结束，也可以因为“最近定时器到期”结束。服务任务没有必要让每个定时器各自运行一条独立线程，也不必每个 Tick 都扫描全部定时器。

活动定时器按到期时间组织，并处理 Tick 回绕问题。这个结构与任务延时列表的思想相通，但两者管理的对象不同。

18.3 启停命令为何是异步的

启动、停止、复位等常见操作把命令送到定时器命令队列，再由服务任务执行。调用方获得成功结果，通常说明命令已经进入队列，不代表服务任务已经完成该动作。

因此“停止命令已经提交”不能被当成“任何回调都绝不会再执行”的同步屏障。若业务需要确认对象可以释放或回调已退出，还要建立明确的完成确认和生命周期协议。

命令中的等待期限通常描述发送方等待命令队列空位的时间，不是软件定时器的周期。这是两个完全不同的等待对象。

18.4 回调为何必须短且不阻塞

所有软件定时器回调通常在同一个定时器服务任务中串行执行。一个回调长时间计算，会延后其他定时器和命令处理；一个回调阻塞，会把整个服务任务一起阻塞。

如果它阻塞等待“由服务任务自己处理队列后才能产生的结果”，还可能形成自我等待。

合理的分工是由回调做简短状态更新或通知业务任务，再让业务任务承担耗时处理。回调虽然运行在任务上下文中，但仍必须遵守共享服务任务的非阻塞约束。官方软件定时器说明

18.5 周期定时器按哪个时刻续期

单次定时器到期后通常变为非活动；自动重装定时器继续安排下一个计划到期时间。

V10.4.6 的自动重装逻辑以前一次计划到期时间加周期推进，而不是简单地等回调结束后再重新等待一整周期。这样可以保持计划时间轴。

假设周期为 10 ms，计划到期为 10、20、30 ms，但服务任务到 35 ms 才获得运行机会。内核可能连续处理已经错过的周期，造成回调短时间集中执行。周期配置正确，不代表回调的实际执行间隔永远等于周期。

18.6 什么决定到期后的实际延迟

影响因素包括 Tick 量化、服务任务优先级、更高优先级任务负载、中断耗时、其他回调占用和命令处理负载。

提高服务任务优先级可以减少一部分调度等待，但会增加它对其他任务的干扰。若一个周期工作有独立的优先级、较长执行时间或复杂阻塞需求，独立业务任务通常更符合其执行语义。

推演检查： 定时器周期为 100 ms，某次回调因系统繁忙晚了 30 ms，后续计划一定整体后移 30 ms 吗？

参考判断： 对自动重装定时器，不应这样理解。内核按原计划到期时间续期，实际回调可能追赶，而不是简单从这次回调结束重新建立周期。

19 Tickless 低功耗：在保持时间正确的前提下休眠

19.1 普通空闲为什么仍然有耗电

应用任务都阻塞后，CPU 可以进入空闲路径。但若节拍仍按固定周期触发，处理器可能不断被唤醒，只为了推进 Tick 并再次发现暂时没有工作。

Tickless Idle 利用已知的空闲时间窗口，抑制不必要的周期性节拍，再结合硬件休眠降低功耗。它没有取消内核时间，而是改变空闲期间推进时间的方式。

19.2 能睡多久，需要知道什么

内核可以根据下一次任务超时、是否存在其他就绪任务、是否有待处理切换等信息估计空闲窗口。只有空闲时间足以覆盖进入和退出低功耗的成本，休眠才有实际收益。

外部中断仍可能提前到来，因此预计睡眠时长只是可休眠上界之一，不是保证一定睡满的承诺。硬件计时器的最大计数长度也可能进一步限制单次休眠。

19.3 为什么睡前必须再次确认

从“计算出可以睡眠”到“执行休眠指令”之间，可能有 ISR 使任务变为就绪。如果仍按旧判断入睡，已经出现的工作就可能被延误。

内核与移植层需要在最后阶段协调中断、调度和待处理状态，重新确认是否仍可睡眠。只有这段过渡受正确保护，才能避免错过唤醒条件。

本书背景的内置 Cortex-M3 路径包含这样的睡前确认；自行扩展低功耗方式时，也必须保留等价的竞争处理。官方低功耗章节

19.4 唤醒后为什么要补偿时间

睡眠期间虽然没有逐次执行普通 Tick 中断，但物理时间仍然流逝。唤醒后需要根据实际经过的时间，补偿内核 Tick，使任务超时和定时器计划继续与现实时间相符。

不能一律补上原来计划睡眠的全部时间，因为外部事件可能提前唤醒；也不能简单从零重启节拍而忽略已经经过的部分周期，否则会造成时间漂移。

补偿必须和最近到期点、待处理节拍相协调，不能随意把 Tick 跳到若干到期任务之后，却不处理它们的唤醒关系。

19.5 Tickless 与具体睡眠模式是两个层次

WFI 等指令用于让处理器等待中断，但实际停止哪些时钟、保留哪些外设、由什么唤醒，取决于芯片电源模式和系统配置。

STM32F103 的睡眠、停止、待机具有不同的时钟和状态保留特性。常见内置 Tickless 方案并不自动替应用完成所有深度低功耗适配。进入停止等更深模式后，如果作为时间基准的时钟停止，还需要可持续计时和唤醒的替代机制，并正确恢复时钟。

因此，“开启 Tickless”不等于“已经达到最低功耗”，也不等于所有外设通信仍能按原配置正常进行。

19.6 降功耗为什么必须回到任务设计

若某任务一直轮询而不阻塞，系统就很难形成可休眠窗口；过于频繁的周期唤醒也会破坏睡眠收益。合理的事件驱动等待，通常是 Tickless 能发挥作用的前提。

最终需要同时评估睡眠功耗、进入退出能量成本、唤醒延迟和时钟恢复时间。更深的睡眠不一定适合更短的空闲窗口。

推演检查： 原计划睡 100 ms，却在 20 ms 时被外部中断唤醒，内核可以直接补偿 100 ms 吗？

参考判断： 不可以。必须按实际经过的时间及节拍边界关系补偿，否则未到期任务会被错误地提前视为到期。

20 内存管理：对象生命周期与分配策略

20.1 先分清任务栈、内核堆和其他存储

任务栈保存任务执行过程中需要的自动存储和上下文；RTOS 堆为动态创建的任务、队列等对象提供存储；全局与静态变量通常由链接布局预先占用 RAM；MSP 还需要独立考虑中断和系统执行的栈空间。

这些空间最终可能都来自同一芯片的 RAM，但管理方式和故障含义不同。任务栈溢出、RTOS 堆分配失败、全局缓冲越界，不是同一种问题。

C 库堆和 RTOS 堆也不一定是同一个分配器。它们是否共享底层区域，取决于所选方案和链接配置。申请与释放必须使用相容的内存管理路径。

20.2 动态内存管理实际在解决什么

分配器要在空闲区域中找到足够大的块，满足对齐和管理开销要求，然后记录哪些部分已经占用。释放时需要识别这块内存并重新纳入空闲结构。

对象请求 100 字节，不意味着分配器只消耗恰好 100 字节，还可能有块头和对齐补齐。多个分散空洞的总和足够大，也不代表存在一块能满足此次请求的连续空间。

20.3 五种 heap 方案为什么并存

方案 主要方法 能否归还并复用 主要限制
heap_1 从预留区域顺序划分 不支持有效释放回收 生命周期中反复创建删除会耗尽区域
heap_2 最适应空闲块，支持分割 支持 不合并相邻空闲块，可能积累碎片
heap_3 包装 C 库分配器 由 C 库实现决定 时序、碎片和容量取决于底层库与链接配置
heap_4 首次适应，合并相邻空闲块 支持 查找耗时与空闲布局有关，不能完全消除碎片
heap_5 类似 heap_4，管理多个不连续区域 支持 使用前需登记区域，一次分配仍需连续块

heap_3 的包装提供任务间调用的保护，不会把 C 库分配器变成固定耗时算法，也不使其适合在 ISR 中任意调用。heap_1 虽然某些源码中存在释放入口，但该方案不提供有效归还内存的能力。

heap_4 能合并物理上相邻且都已释放的块，不能跨越仍被占用的块。heap_5 能统一管理分离的 RAM 区域，但不能把跨越地址空洞的两块内存拼成一块连续对象。

以上方案的整体差异可对照 官方内存管理说明，具体行为以本笔记核对的 V10.4.6 实现为准。

20.4 内存碎片为什么总量足够仍会失败

假设有两块空闲区域，各 400 字节，中间隔着一块仍被使用的存储。总空闲量为 800 字节，但一个需要连续 600 字节的对象仍然无法放下。

相邻块合并只能在中间那块也释放后发挥作用。长期混合不同大小和生命周期的对象，可能形成难以合并的布局。

因此，观察堆总空闲量只是第一步，还要考虑最大连续空闲块、历史最低余量、创建销毁频率和对象寿命分布。

20.5 为什么任务安全不等于实时性充分

任务安全说明多个任务通过同一管理规则调用分配器时，不容易破坏其内部结构。但分配器仍可能遍历空闲块，耗时会随着布局变化。

在关键周期中反复分配和释放，会把这类变化引入响应时间。若对象集合可以预先确定，提前分配或使用固定资源池，可以使生命周期和失败边界更容易分析。

普通 FreeRTOS 堆分配不应在 ISR 中使用。系统中断可以发生在分配器维护内部状态期间，而且其执行成本与 ISR 的短时、可分析要求通常不相容。

20.6 静态创建也需要生命周期纪律

静态对象的存储在对象存活期间必须一直有效。不能因为“不经过堆”就把一段即将失效的临时存储交给长期存在的任务。

删除对象后，其他任务或 ISR 还保存旧句柄、旧缓冲指针，同样可能产生悬空访问。内存回收必须与所有使用者完成退出相协调。

这与队列指针、定时器异步停止和任务删除都有关：资源释放前要证明没有后续访问者，而不能只证明发出了一个停止命令。

推演检查： 使用 heap_4 后，就可以认为动态内存永远不会因为碎片分配失败吗？

参考判断： 不可以。它能合并相邻空闲块并减少碎片，但无法跨越仍被占用的块，也无法突破总容量和连续块大小限制。

B. 推演一：DMA 接收完成到任务处理

假设高优先级解析任务正在等待通知，DMA 正在填充接收缓冲区。

  1. DMA 完成，硬件产生中断；ISR 先确认完成状态和需要处理的硬件标志。
  2. ISR 通过符合优先级规则的通知操作，更新解析任务通知状态。
  3. 若解析任务正在等待这个通知项，内核解除等待，使它就绪，或在调度挂起时登记待就绪。
  4. ISR 按移植要求提出切换请求；必要的中断处理结束后，PendSV 完成上下文切换。
  5. 解析任务取得 CPU 后读取数据；这一刻必须保证 DMA 不会覆盖它仍在使用的区域。
  6. 解析完成后，按业务协议把缓冲区归还给接收侧。

链路中的两个独立问题是“通知有没有送到”与“数据存储是否仍归接收者安全使用”。只解决前者，仍可能出现数据损坏。

C. 推演二：带期限等待队列数据

任务最多等待 50 个 Tick。内核同时登记队列等待关系与超时关系。数据先到时，事件路径结束等待并清理超时记录；期限先到时，时间路径清理事件关系并让任务恢复运行资格。

如果任务被事件唤醒后暂时没有获得 CPU，另一个执行者可能先消费数据。恢复执行的任务仍需重新确认队列状态，并按剩余等待期限处理。

因此，应区分三个时刻：发生唤醒条件、任务变为就绪、业务操作实际完成。它们并不必然重合。

D. 推演三：定时器回调变慢会影响谁

一个回调持续计算很久，首先拖住同一个服务任务中的其他回调和命令处理。ISR 提交的事件组置位请求若也使用该服务任务，就可能一并延后。

命令消费变慢还可能使命令队列积压，任务侧发送命令可能等待，ISR 侧提交可能失败。一个局部的长回调，可能沿共享服务任务与命令队列扩散到多个业务模块。

这类问题不能只看“该定时器自己的周期是否足够长”，还要看它占用的是谁的执行环境。
