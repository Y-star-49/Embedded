## 学习范围与阅读约定

本文系统整理 **C11 / C17 中与嵌入式开发密切相关的理论知识和关键字**，从语言规则逐步连接到编译、存储、硬件访问与并发模型。涉及裸机、RTOS、缓存或多核时，分别说明成立条件。

正文以概念、原理、适用边界和概念推演为主；关键字讲解配少量独立的 C 代码片段，用于辨析语义。各片段分别阅读，不组成完整程序。阅读重点是解释规则如何成立，以及一种机制为什么不能代替另一种机制。

数值推演默认采用常见 MCU 模型：一个字节为 8 位，`int` 为 32 位，并采用常见整数表示。**这些是例子的条件，不是 C 对所有平台的统一保证。** `long`、指针、枚举、结构体布局和浮点运算代价都需要结合实际工具链确认。C23 的变化集中在附录中辨析，不默认现有工程已启用 C23。

## 1. 编译与运行：一份 C 文件怎样变成 MCU 的行为

### 1.1 从“编译通过”到“能够运行”，中间还有什么

C 源文件描述的是类型、对象和操作，处理器执行的是机器指令。两者之间需要经过翻译、符号解析和地址安排；运行前还要建立栈及对象初值等条件。语法正确只是这条链路中的一个前提。

常见构建流程是：**预处理 → 编译 → 汇编 → 链接 → 生成烧录映像**。工具可能把若干步骤合并，但各步骤解决的问题不同。

- 预处理选择当前配置下真正参与构建的内容，展开头文件和宏。
- 编译检查语言规则并把计算转换为目标机器操作；优化通常在这一过程中发生。
- 汇编产生目标文件，里面除了机器码，还有尚待链接解决的符号与重定位信息。
- 链接把多个目标文件和库组合起来，解析符号，并依据链接脚本安排地址。
- 映像转换工具按下载需求产生 BIN、HEX 等格式。ELF 通常还保留段、符号及可选调试信息。

因此，“找不到声明”“找不到定义”“程序能烧录却无法启动”分别可能发生在不同层次，不能都归结为语法错误。

### 1.2 复位后为什么不能直接假定进入主函数

常见裸机系统先进入复位处理流程，建立栈、初始化必要运行环境，再进入应用入口。静态对象的初值需要落到实际内存中；中断向量、时钟和存储器配置也可能参与启动。

具体步骤及顺序由架构、启动文件和运行库共同决定。C 标准不规定 MCU 向量表的形状，也不规定每颗芯片的复位地址。裸机常采用独立式环境，不能把桌面操作系统提供的所有运行条件直接套过来。

### 1.3 如何判断错误所处阶段

| 现象 | 优先检查 |
| --- | --- |
| 类型未知、声明冲突 | 头文件、条件编译、声明是否一致 |
| 未定义符号、重复定义 | 哪些目标文件参与链接、定义数量、链接属性 |
| 启动即异常 | 向量、栈、入口、内存布局、启动初始化 |
| 运行后外设不响应 | 寄存器、时钟、引脚复用、访问时序 |

### 推演检查

一个驱动函数在头文件中有声明，调用处也能正常编译，链接时却提示找不到它。这说明什么？

### 参考判断

调用处已经获得足够的类型信息，但最终链接输入中没有可匹配的实现。可能是对应源文件未参与构建、实现被条件编译排除，或名称与链接属性不一致。反复添加头文件通常不能解决缺失定义。

## 2. 声明、定义与头文件：多个文件怎样共享同一份约定

### 2.1 声明告诉编译器什么，定义真正提供什么

声明描述一个名字的类型及相关属性，让编译器能够检查使用方式。定义进一步提供对象本身或函数实现。一个定义通常也是声明，但声明不一定构成定义。

对普通全局变量而言，其他文件需要知道它的类型，实际存储通常只应由一个源文件提供。对函数而言，调用者需要正确原型，链接阶段需要相应实现。让每个调用文件各写一份声明，很容易造成类型分歧，所以应共用头文件。

源文件预处理后形成的翻译单元，是许多语言检查和内部链接规则的边界。两个翻译单元可以分别通过编译，却因为同一接口的声明不兼容而形成错误程序；链接器并不总能替代完整的类型检查。

### 2.2 为什么头文件保护解决不了所有重复定义

头文件保护主要防止同一头文件在**同一个翻译单元**中被重复展开。它不阻止两个源文件分别包含同一份内容。

如果头文件放入普通外部对象定义，两个翻译单元仍可能各自产生定义。把对象改为文件级 `static` 则会产生各自独立的对象，也不能得到原本想要的“一份共享状态”。

适合公开的是类型、必要常量约定、函数声明和有意公开的对象声明。内部状态留在实现文件，可以缩小依赖范围。某些小型内联实现可以放在头文件中，但须理解其链接语义。

### 2.3 `extern` 不等于“这一句绝不产生定义”

`extern` 常用于声明其他位置定义的对象，但带初始化的对象声明仍可能构成定义。另一个细节是文件作用域的暂定定义：没有显式初始化的某些对象声明，最终仍承担定义的作用。

工程上不能靠“这一行没有赋初值，所以只是声明”来区分。最可靠的认识是明确：哪个翻译单元拥有对象，其他文件通过什么接口使用它。

### 推演检查

一个头文件定义了文件级 `static` 对象，两个源文件都包含它。为什么两个源文件使用相同名字，却可能读写不同的对象？

### 参考判断

每个包含该头文件的翻译单元可能拥有自己的内部链接对象。名字相同不表示对象相同。若要求共享同一对象，应明确其唯一的定义位置，并通过一致的声明或公开操作访问。

## 3. 类型与表示：一个数值为什么不只是若干二进制位

### 3.1 类型同时决定范围、运算与访问方式

传感器原始值、温度差和缓冲区长度可能都占用整数存储，但含义不同。原始寄存器值通常关注位模式，温度差可能为负，长度还参与地址计算。类型选择应从含义、范围和后续运算共同出发。

`char`、`short`、`int`、`long`、`long long` 并不在所有实现上对应同一组固定宽度。C 规定最低能力和类型关系；目标 ABI 决定具体大小。`sizeof` 以 C 字节为单位，而一个字节具有多少位由 `CHAR_BIT` 描述。

固定宽度类型如 `uint16_t` 在实现提供它时，明确表示恰好 16 位的无符号整数；精确宽度类型并非所有实现都必须提供。`size_t` 用于对象大小和相关计数，`ptrdiff_t` 用于合法指针相减的结果，它们也不是固定为 32 位。

### 3.2 符号性与“看起来一样的字节”

在常见 8 位模型下，255 可以由无符号 8 位整数表示，却超出有符号 8 位整数的正数范围。相同存储位在不同类型下可能有不同解释，后续提升和比较也可能不同。

普通 `char` 与 `signed char`、`unsigned char` 是不同类型；普通 `char` 的符号性由实现决定。文本与原始字节流应在概念上区分，不能因为数据以字节为单位存储，就假定普通 char 的值总是非负。

### 3.3 浮点数解决范围问题，也引入精度与成本问题

`float`、`double` 表示浮点类型。常见二进制浮点只能精确表示部分数值，十进制小数可能发生舍入；连续累加可能积累误差。浮点数的有效精度与可表示范围是两个指标。

硬件是否支持某类浮点运算、编译器使用什么调用约定、库函数是否引入软件运算，决定实际成本。`double` 不应被简单理解为“肯定只是占两倍空间”或“只要有 FPU 就没有代价”。

定点方案把物理量按约定比例映射为整数，例如以毫伏保存电压。它便于控制表示和成本，但仍需推导缩放过程中的溢出与舍入。

### 推演检查

ADC 原始值能放入 16 位整数，转换成微伏时为什么可能需要更宽的中间类型？

### 参考判断

存储原始值所需的范围，不等于原始值乘以比例系数时所需的范围。应先确定最大乘积，再选择中间运算类型；最后结果很小，也不能证明中间计算不会溢出。

## 4. 整数提升与转换：为什么结果变量足够大，计算仍会错

### 4.1 先确定表达式类型，再考虑存到哪里

CPU 执行计算之前，C 已经规定操作数如何提升、如何转换为共同类型。一个窄类型对象参与运算时，运算通常不会一直停留在它原来的宽度。

整数提升常把小整数类型提升为 `int`；若 `int` 不能表示其全部值，则提升为 `unsigned int`。随后，许多二元运算还会经过通常算术转换。**表达式的计算类型主要由操作数和运算规则决定，接收结果的变量不会自动把此前的运算变宽。**

例如在 32 位 `int` 能容纳全部 16 位无符号值的平台，两项最大为 65535 的 16 位无符号数，乘法可能在有符号 `int` 中进行。最大乘积 4294836225 超出 32 位有符号范围。即使之后存入 64 位对象，错误也已经发生。

### 4.2 有符号、无符号和窄化不能混为一谈

| 情况 | C11 / C17 中需要记住的规则 |
| --- | --- |
| 无符号运算超出本类型范围 | 按该无符号类型的模数回绕 |
| 有符号算术结果超出可表示范围 | 通常属于未定义行为，不能依赖硬件自然回绕 |
| 整数转为无符号类型 | 按目标类型范围进行模意义下的转换 |
| 数值不能由目标有符号类型表示 | 结果由实现定义，或产生实现定义的信号 |
| 浮点转整数 | 丢弃小数部分；越出适用范围不能靠普通窄化经验解释 |

混合符号比较尤其容易出错。当负的有符号数被转换为无符号数时，它可能变成很大的正值。判断“错误码是否小于缓冲区长度”之前，必须先检查两侧类型，而不是只看数学含义。

### 4.3 强制转换是选择语义，不是修复证明

强制转换可以表达已经验证过的范围收缩，也可以在运算之前改变参与运算的类型。但它不会恢复已丢失的高位，也不会补救已发生的未定义行为。

字面量也有类型。十进制与十六进制整数字面量选择类型的候选规则并不完全相同，数值大小会影响最终类型。不能只凭是否写了后缀判断整个表达式是否安全，应结合实际类型和范围推导。

### 4.4 复合赋值：计算类型与存储类型可能不同

假设两个操作数都是 16 位无符号整数，值分别为 1 和 2，而目标平台的 `int` 为 32 位。把两者相减并写回第一个对象，过程需要分开理解：

1. 整数提升使两个操作数先转为能够容纳其全部值的 `int`。
2. 减法在该类型中得到 −1，这一步没有发生有符号溢出。
3. 写回 16 位无符号对象时发生转换，结果成为 65535。

这说明“出现回绕值”不一定意味着算术运算本身在窄无符号类型中完成。问题也可能来自合法的负结果被转换回无符号存储类型。写回后检查对象是否小于零，已经不能恢复此前的负值信息。

复合赋值需要同时分析左侧对象类型、运算时的类型和写回转换。判断合法性与判断是否符合业务含义是两个层次：模转换可以是语言允许的行为，却不符合调用者要求的范围。

### 4.5 窄化是信息丢失，不是数值压缩

整数从较宽范围转换到较窄的无符号范围，多个不同原值可能映射到同一个结果。例如转换到 16 位无符号类型后，1 和 65537 都得到 1；转换结果本身无法说明此前是否超出目标范围。

所以，范围验证应发生在信息丢失之前。先转换再检查目标值，通常无法重建原始事实。即使计算过程全部合法，最后存入较窄对象、传给较窄形参或写入较窄硬件字段，仍可能丢失信息。

类型范围、算法允许范围和硬件字段范围也不一定相同。一个值可以被 32 位类型完整表示，但只允许落在 0—1000 的算法范围内；另一个值可以满足算法，却无法由目标寄存器编码。每一层约束都要独立成立。

### 推演检查

一个整数表达式先得到很大的乘积，再除以较大分母，最终结果只有 1000。能否据此认为 16 位中间计算足够？

### 参考判断

不能。每一步都必须合法，最终范围不能约束先前中间值。调整乘除顺序可能降低溢出风险，却又可能提前截断精度；应同时推导最大值、舍入误差与所需中间宽度。

## 5. 表达式与位运算：写法紧凑为什么不等于行为简单

### 5.1 优先级、结合性和求值顺序是三件事

优先级决定表达式如何分组，结合性处理同级运算符的分组，求值顺序决定各部分何时被计算。加括号能澄清分组，却不一定规定独立操作数或函数实参的求值先后。

同一个对象在缺乏必要先后关系的求值中被修改，又被另一个求值读取或修改，可能触发未定义行为。多个参数表达式彼此独立、各自没有冲突时，求值顺序未指定也不等于程序必然错误。

复合赋值会对左侧定位表达式求值一次，但仍包含必要的读取、运算、转换和存储；它既不绕过整数提升，也不自动成为原子操作。

### 5.2 位运算用于描述位模式，逻辑运算用于判断真假

按位与、或、异或、取反逐位操作；逻辑与、或、非依据真假产生结果。逻辑与、逻辑或还有短路规则：前一条件已决定结果时，后一条件不再求值。按位运算不能替代这个求值约束。

掩码用于指定关注哪些位。读取某状态位时，通常关注结果是否非零，而不是要求按位结果恰好等于数值 1。取反窄整数前还要考虑整数提升，否则“取反一个字节”的直觉与表达式实际宽度可能不同。

### 5.3 移位必须先回答三项边界

1. 左操作数经过提升后是什么类型、多少位？
2. 移位次数是否非负，且严格小于该类型宽度？
3. 操作数的符号和数值是否满足该移位操作的要求？

在本文的 C11 / C17 范围内，对负的有符号值右移属于实现定义；对负值左移、或某些超出规定可表示条件的有符号左移，则不能依赖。位掩码运算应明确无符号语义和有效位宽。

### 推演检查

某状态寄存器第 5 位为 1，按位检测得到 32。为什么拿这个结果与 1 比较会误判？另一个问题是，为什么“设置一位”也可能丢失别人的修改？

### 参考判断

按位检测保留该位原来的权重，结果非零就表示条件成立。设置一位若采用读—修改—写序列，读取与写回之间可能被中断或硬件修改；写回旧快照会覆盖新状态。语言中的位运算和系统中的并发安全必须分开判断。

## 6. 控制流：判断、循环与状态机如何约束执行时间

### 6.1 分支决定路径，状态描述跨时间的记忆

`if` 和 `else` 根据条件选择路径，`switch` 根据整数控制值分派到 `case`；`default` 处理未匹配情况。分支只描述当前一次执行，而状态机还记录“系统已经走到哪里”，使下一次输入获得正确解释。

状态机把历史压缩为有限状态，再由输入和当前状态决定下一状态及动作。把历史散落在多个独立标志中，容易形成互相矛盾的组合；明确状态集合与转移条件，可以分析哪些状态可达、哪些转移应被拒绝。

### 6.2 循环结束条件必须包含环境不满足的情况

`for` 适合有明确推进关系的遍历，`while` 先检查条件，`do` 至少执行一次循环体。`break` 退出最内层循环或 `switch`，`continue` 进入下一次循环的相应步骤。

轮询外设状态时，不能只考虑“成功后如何退出”，还要考虑外设掉线、时钟未开或状态永远不改变。超时不是附加装饰，而是接口时间上界的一部分。

节拍回绕需要在明确的无符号模数及测量窗口内推导。用模减法计算经过时间，可以跨越一次回绕，但仍需保证真实间隔没有跨过不可区分的完整周期；某些判断时间先后的方法还要求比较距离小于半个模数范围。

### 6.3 `return` 与 `goto` 的用途边界

`return` 结束当前函数，不会自动停止 DMA、释放锁或归还外设所有权。提前返回的每条路径都要满足资源约定。

`goto` 是同一函数内的控制转移，可用于汇合错误清理路径。它本身不是错误来源；真正需要检查的是跳转是否越过必要初始化、是否造成重复释放，及是否让控制关系难以追踪。

### 6.4 阻塞、非阻塞与时间上界

阻塞描述调用在条件满足前不返回。忙等是阻塞的一种实现方式，它持续占用处理器检查条件；任务挂起也可能使调用保持未完成，却允许其他任务运行。因此，“调用尚未返回”和“处理器持续忙碌”不是同一个判断。

非阻塞操作在当前条件不足时返回，由状态对象保存进度，后续再继续。它将一次长过程分解为多个短步骤，因此需要明确未完成、已完成、失败等状态，以及哪些资源在两次调用之间仍被持有。

非阻塞并不自动等于实时。若某个短步骤长时间得不到调度，总完成时间仍可能没有上界。分析时间约束时，需要同时考虑单次执行时长、等待条件、调用间隔和最大重试次数。

### 推演检查

一个操作每次调用都很快返回，但必须被重复调用才能完成。能否仅据此证明它一定在规定时间内完成？

### 参考判断

不能。还需要知道每次调用之间的最大间隔、完成所需的最大步骤数，以及外部条件是否有满足时限。单次执行上界只是总响应时间证明的一部分。

## 7. 函数与回调：一次调用究竟传递了什么

### 7.1 C 按值传参，地址也作为值传递

函数接收实参值形成的形参。形参的改变一般不改变调用者用于传值的对象。传递指针时，复制的是指针值；双方可以因此访问同一个被指向对象，但形参指针本身仍是独立的参数对象。

这解释了两种不同需求：修改缓冲区内容，需要能够访问那块存储；修改调用者保存的缓冲区地址，还需要访问调用者的指针对象。不能把二者都笼统称为“传了地址，所以都能改”。

在 C11 / C17 中，显式以 `void` 表明无参数的函数原型，与旧式空参数列表声明的含义不同，后者不提供完整的参数类型信息。接口应让调用者获得完整原型。C23 对空参数列表的规则有所调整，阅读旧工程时要先确认语言模式。

### 7.2 调用成本来自 ABI，而不是函数名长度

ABI 规定参数和返回值如何放入寄存器或内存、哪些寄存器由谁保存、栈怎样对齐等。结构体按值传递可能产生复制，也可能被优化或通过特定 ABI 机制传递，不能单凭源代码长度估计成本。

可变参数函数尤其依赖约定。类型信息不再像固定形参那样完整，实参还会发生默认提升；格式化输出必须用正确格式解释对应类型。错误格式可能导致错误取参，而不只是显示不好看。

### 7.3 函数指针把行为变成接口的一部分

函数指针把一个可调用函数作为值传递，使调用方可以通过统一的兼容类型选择不同实现。回调是在约定事件发生时由另一段程序发起的调用。它们表达“调用哪种行为”，并不自动携带对象状态。

回调通常还需要上下文：对应哪个设备、哪块缓冲区、当前处于什么状态。函数类型必须兼容，状态对象必须活得足够久，还要明确回调在主循环、任务还是中断中执行。普通对象指针与函数指针的互转也不是可随意依赖的通用保证。

### 7.4 注册回调不等于拥有回调所需的资源

一个异步驱动通常保存两类信息：将来要调用的函数，以及该函数要访问的上下文。函数仍存在，不代表上下文仍存在；设备已经销毁，或注册时使用的局部对象已经失效，都会使后续调用失去合法的数据来源。

注销也要定义完成条件。仅清除“以后不要再调用”的标志，可能阻止新调用，却不保证已经开始的调用结束。安全释放上下文前，需要确认不会再启动新回调，并且现有调用不再持有它。这个过程可能借助任务协作、引用管理或驱动提供的取消完成机制，具体取决于执行环境。

同样，回调收到缓冲区地址，并不自动拥有无限期保存它的权利。若缓冲区只在回调期间借用，函数返回后驱动就可能复用它；需要长期使用时，必须通过约定取得所有权或复制有效内容。函数指针解决行为选择，资源协议解决数据何时仍然可用。

### 推演检查

一个回调原先在任务中调用，后来改到中断中调用，函数签名完全没变，为什么仍可能出问题？

### 参考判断

类型兼容只覆盖接口的一部分。中断中的可阻塞性、允许调用的系统服务、栈预算和并发关系都发生了变化。若回调打印、等待互斥量或访问未保护的共享状态，原有执行环境约定就被破坏。

## 8. 指针：有地址为什么仍不一定能访问

### 8.1 指针的有效性包含地址之外的条件

指针帮助程序间接访问对象。判断一次访问是否成立，至少要检查：目标对象是否存在、是否在生存期内、地址是否正确对齐、范围是否足够、访问类型是否允许、权限是否匹配。

因此，非空检查只能排除一种特定情况。已经释放的对象、越界地址、失效的局部对象、无法访问的外设区域，都可能对应非空指针。

空指针表达“不指向有效对象或函数”的语言含义。它的表示不由“所有硬件都把地址零保留不用”来定义；某些 MCU 地址零还映射真实存储。不要把空指针语义与芯片物理地址图混为一谈。

### 8.2 指针运算依赖对象边界

对某类型指针前进一个元素，移动的是该类型元素的大小。合法的数组指针运算围绕同一数组对象及其尾后位置展开，尾后指针可以用于边界比较，但不能解引用。

同一数组内的指针相减可以得到元素距离。两个毫无关系的对象即使物理上相邻，也不因此成为可任意跨越、排序或相减的一整块数组。

`void` 指针适合在接口中传递通用对象地址，但它没有完整的元素类型。标准 C 不提供对 `void` 指针的普通元素步进，也不能直接通过它访问某个具体对象的值；需要恢复合适类型并满足访问条件。

### 8.3 指针与整数转换属于平台敏感边界

嵌入式寄存器访问常把固定地址映射为指针，这是实现与硬件共同约定的用法。整数能装下一个地址，不代表任意整数都能变成有效对象地址。

可选的 `uintptr_t` 用于满足特定对象指针转换需求，但它不能自动解决内存权限、对象生存期、地址空间或函数指针问题。把指针塞进普通 32 位整数，在某个 MCU 上可用，也不能作为跨平台规则。

### 推演检查

函数返回了局部数组的地址，调用者发现内容暂时还正确。为什么这个现象不能证明接口有效？

### 参考判断

数组的自动存储期已经结束。原存储尚未被覆盖，只是某次运行中的偶然现象；后续调用、中断或优化都可能改变它。地址数值没有立刻变化，不代表对象继续存在。

## 9. 数组与缓冲区：连续存储为什么不等于自带长度

### 9.1 数组对象与指针对象保存的东西不同

数组对象包含连续排列的元素；指针对象保存用于指向对象的值。数组在许多表达式中会转换为指向首元素的指针，这种转换并不意味着数组本来就是指针。直接对数组取地址时，得到的是指向整个数组的指针，步进单位与指向首元素的指针不同；`sizeof` 等场合也不会按普通数组到指针转换处理。

函数形参采用常见数组形式时会调整为指针类型，因此函数通常不能只凭该形参自动恢复调用方数组长度。接口需要额外长度、约定固定尺寸，或传递包含长度信息的描述对象。

### 9.2 `sizeof` 必须看见真正的对象或类型

`sizeof` 是运算符，结果类型为 `size_t`。它作用于真正数组对象时可反映整个数组占用空间；作用于指针时只反映指针自身大小。

对普通非变长类型，`sizeof` 的操作数通常不求值，结果可在编译期确定。涉及变长数组类型时有不同规则，相关表达式可能需要运行时求值。不能把“永远不执行里面的内容”当作无条件结论。

### 9.3 多维数组是数组嵌套，不是多级指针

一个二维数组由若干行数组连续组成，行的长度决定跨行步长。指向指针的对象则描述另一种组织关系：它指向的对象本身是指针，不能仅因“都有两层下标”就互换。

多维数组的元素连续性、行长度和下标层次共同决定地址步长。逻辑上的二维数据可以采用多种存储组织；接口必须与实际对象类型一致，不能仅凭数据含义推断指针类型。

### 9.4 边界检查必须保护计算本身

检查起点加长度是否超出容量时，那个加法自身可能先溢出。更稳妥的推理顺序是先证明起点不超过容量，再在剩余容量内判断长度；计算总字节数时，也要在乘法发生前检查元素数与单元素大小的关系。

### 9.5 容量、有效长度与表示能力是三个独立约束

容量表示已经存在的存储边界，有效长度表示其中当前可使用的数据范围，长度类型的表示能力决定接口能表达多大的数。扩大长度类型不会扩大存储，扩大存储也不会保证内部数据已经有效。

若缓冲区同时容纳头部和载荷，应先证明固定开销不超过总容量，再在剩余空间内判断载荷长度；若还包含尾部或对齐填充，也必须纳入同一容量证明。仅验证最终总长度还不够，因为计算总长度的加法可能已经回绕。

复制涉及两个对象，源区域必须有足够的可读数据，目标区域必须有足够的可写空间。容量检查正确也不代表复制时机正确：若另一个执行者仍在修改源内容，还需要同步或所有权约定。

### 9.6 `sizeof` 的简例：结果由操作数类型决定

```c
#include <stddef.h>

int values[8];
int *position = values;

size_t array_bytes = sizeof values;
size_t pointer_bytes = sizeof position;
```

这里的 `size_t` 由标准头文件 `<stddef.h>` 提供。`array_bytes` 为 8 个 int 对象所占的总字节数，`pointer_bytes` 为一个指针对象自身的大小；后者不能反推出数组长度。示例中的两个大小也不应直接预设为某个固定数值。

把数组作为常见数组形参传入函数后，形参会调整为指针类型；函数内再对该形参使用 `sizeof`，看到的是调整后的类型。这个差异来自类型规则，不是函数“忘记了”某个隐藏长度。

### 推演检查

一个二维数据区域的行数和列数都分别合法，为什么行数乘列数得到的元素总量仍可能错误？

### 参考判断

单个参数合法不保证组合运算合法。乘积可能超出计算类型或分配大小类型的范围，随后造成小分配、大写入。应同时检查每个维度、乘积、步长及坐标偏移所需的范围。

## 10. 字符串与字节流：为什么收到一段数据还不能直接当文本

### 10.1 C 字符串依赖终止符，通信数据依赖协议长度

C 字符串是在可访问的字符序列中以空字符结束的表示。字符指针本身不携带长度，也不证明后方存在终止符。

一个长度明确的接收区域可能包含二进制数据、部分文本或尚未完成的消息。对其调用需要字符串的处理操作，可能一直读到缓冲区之外才遇到零值。二进制载荷也可能在中间包含零字节，不能用字符串长度代替协议长度。

### 10.2 四个“长度”应分开

| 名称 | 实际含义 |
| --- | --- |
| 缓冲区容量 | 这块存储一共能容纳多少字节 |
| 当前有效长度 | 其中已有多少字节属于有效输入或输出 |
| 字符串长度 | 第一个终止空字符之前有多少个字节单元 |
| 文本字符数量 | 按具体字符编码解释后有多少字符，未必等于字节数 |

UTF-8 汉字可能占多个字节，所以显示字符数、发送字节数与数组容量不是同一个量。截断文本时还可能截在编码序列内部。

### 10.3 复制、格式化与重叠各有边界

字符串操作要为终止符留出空间，并明确发生截断时的处理。并非所有“带长度参数”的函数都保证目标形成完整字符串，必须看具体接口语义。

`memcpy` 按字节复制，源与目标重叠不满足它的要求；需要支持重叠时，应采用对应语义的操作，例如 `memmove`。这两者都不会自动理解数据结构中的指针所有权。

格式化输出还会带来栈、运行时间和库体积成本。输出格式与实参类型必须匹配，固定宽度整数可借助标准提供的格式约定，不能凭某个类型“看起来等于 unsigned long”就混用。

### 10.4 格式化返回的长度，不一定是实际写入的长度

在参数有效、没有编码错误并符合标准库语义的前提下，`snprintf` 返回的是空间足够时原本需要输出的字符数，不含终止符；目标容量大于零时，它限制写入并为终止符保留位置。因此必须分别处理失败、完整输出和截断。[WG14 N1570 第 7.21.6.5 节](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

假设容量为 16 字节，返回值为 20：这表示完整内容原本需要 20 个字符，当前最多保存了 15 个字符和终止符。若直接把 20 当作后续读取长度，就会越过这块缓冲区。输出没有写越界，不代表后续使用返回值就安全。

接口应先识别负返回值，再判断非负结果是否达到容量。截断后的文本是否仍有业务意义也要单独判断：调试日志可能允许缩短，设备命令、长度字段或校验字段通常不能任意截断后继续发送。

还应区分字符串字面量与可写字符数组。字面量可能被共享或安排在只读存储；通过指针尝试修改它属于未定义行为。复制到独立可写数组后修改，操作的是另一份对象，仍需满足容量与终止符要求。

### 推演检查

接收缓冲区容量为 64 字节，本次收到 64 字节文本。为什么再补一个终止符会越界？

### 参考判断

64 个存储位置已经全部被有效输入占用。若要在同一缓冲区构造字符串，必须事先保留终止符位置、扩容，或采用长度明确的处理方式。把最后一个字节改成零虽然避免越界，却会丢弃输入，必须作为有意设计的截断策略。

## 11. 结构体、对齐与位域：逻辑上相邻的数据怎样放进内存

### 11.1 结构体把相关状态变成一个对象

结构体类型把若干有名字、可具有不同类型的成员组成一个整体。每个成员保留自己的类型和存储，整体对象便于表达相关数据之间的关系，也使赋值、传参与实例管理具有明确的对象边界。

结构体的逻辑成员顺序明确，但成员之间和末尾可能存在填充。对齐既影响访问效率，也可能决定某些机器访问是否合法。结构体大小因此不一定等于成员大小之和。

### 11.2 布局不是天然的通信协议

直接发送结构体内存，可能把填充字节、目标字节序、枚举尺寸和指针值一起暴露出去。更换编译器或调整成员后，接收方看到的格式还可能改变。

协议需要明确每个字段的宽度、顺序、字节序和编码规则。对象内存布局描述“本程序怎样存”，序列化描述“双方约定怎样交换”，两者职责不同。

结构体赋值会复制成员的值；若成员含指针，复制后仍可能指向同一资源，并不会自动复制指向的整块内容。逐字节比较也不等价于逐成员比较，因为填充和某些值表示可能造成差异。

### 11.3 位域和紧凑布局为什么需要谨慎

位域让一个整数存储单元内的若干位具有成员名，但分配顺序、跨单元规则等与实现相关。位域成员也不能像普通对象那样逐个取地址。

编译器的紧凑布局扩展可以减少填充，却可能产生未对齐成员和访问代价。它不会自动统一大小端，也不会自动满足外设访问宽度。访问硬件寄存器的位域还可能隐含读取或涉及相邻位域，不能从一个成员赋值推断总线只写了那一个位。[GCC 对 volatile 位域访问的说明](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html)

### 11.4 用一个布局例子理解中间填充与尾部填充

假设某 ABI 中，三个成员依次为：1 字节标志、4 字节且要求 4 字节对齐的计数值、2 字节且要求 2 字节对齐的状态值；结构体按最强成员要求对齐。

| 部分 | 示例字节偏移 | 原因 |
| --- | --- | --- |
| 标志 | 0 | 起点即可满足其对齐 |
| 中间填充 | 1—3 | 让计数值从 4 的倍数偏移开始 |
| 计数值 | 4—7 | 连续占用 4 字节 |
| 状态值 | 8—9 | 偏移 8 满足 2 字节对齐 |
| 尾部填充 | 10—11 | 让结构体数组的下一元素仍从合适边界开始 |

成员有效大小相加为 7 字节，结构体却占 12 字节。尾部填充的意义，在结构体组成数组时尤其明显：数组元素的步长就是结构体大小，步长必须让后续元素也满足对齐。

在上述假设下，改为先放计数值、再放状态值、最后放标志，可能把大小降到 8 字节。这解释了为什么成员顺序影响内存占用，但改动顺序也会改变偏移和 ABI。已经被持久化格式、外部二进制接口或硬件映射依赖的布局，不能只为省空间而随意调整。

### 推演检查

一个结构体加上紧凑布局属性后，尺寸恰好等于协议包长度，能否直接认定其内存就是可移植的协议格式？

### 参考判断

不能。还需解决字节序、各类型表示、位域布局、未对齐访问及版本兼容。长度相同只证明占用空间相同，不能证明每个字节具有双方约定的含义。

## 12. 联合体、枚举与类型别名：怎样表达“同一对象的不同角色”

### 12.1 `union` 共享存储，适合互斥的数据形态

联合体成员共享同一块存储，整体需要容纳相应成员并满足对齐。当一个对象在不同阶段只需保存不同形态中的一种时，可以用联合体表达这种存储复用。

联合体本身不记录“当前哪一种形态有效”。通常还需要类型标签，并保证标签与载荷一致。只节省存储却不管理状态，会把内存优化变成解释错误。

C 对读取非最近写入成员有对象表示重解释的相关规则，但结果受表示、有效字节和陷阱表示等限制；它不是任意类型之间可靠的数值转换。C 与 C++ 对此也不能直接混用结论。可移植的协议解析应明确字节意义，而不是把联合体当作普遍的转换器。

### 12.2 `enum` 命名状态，不能代替输入验证

枚举让空闲、发送中、错误等状态具有名字，减少用裸数字表达语义的困难。在 C11 / C17 中，枚举常量与枚举类型的兼容整数类型有不同规则；不能笼统断言所有枚举对象必定是固定 32 位。

枚举也不自动成为强约束的封闭集合。来自通信、持久化或强制转换的数据仍需验证有效范围；异常状态需要明确定义处理方式。把枚举直接作为线上协议字段，还会引入布局与版本问题。

### 12.3 `typedef` 给类型命名，不建立新隔离层

类型别名让接口更能表达意义，例如长度、时间或设备句柄，但通常不会创建一个与原类型不兼容的新类型。两个别名即使名字分别表示毫秒和微秒，也不自动阻止混用。

别名还可能隐藏指针层次。给一个“指针类型的别名”加 `const`，约束的是别名所代表的整体类型，不应机械理解为自动给被指向对象加只读限制。复杂类型命名后更易读，也更需要先弄清它究竟代表什么。

### 12.4 `struct`、`enum` 与 `typedef` 的简例

```c
enum State { STATE_IDLE, STATE_BUSY };

typedef struct
{
    enum State state;
    unsigned int count;
} Record;
```

`enum` 给状态值命名；`struct` 定义成员同时存在的聚合类型；`typedef` 为该结构体类型建立别名 `Record`。这一段只建立类型和枚举常量，没有定义一个 Record 对象，也没有为“一个记录实例”分配存储。

若将多个成员置于 `union` 中，含义会变成共享存储，而不是同时拥有独立的成员存储：

```c
union Value
{
    int integer;
    float real;
};
```

程序仍需另行约定当前应按哪个成员解释内容。联合体没有自动的运行时类型标签，不能因为两个成员都能写进同一块空间就同时保留两份独立值。

### 推演检查

一个带类型标签的联合体，标签表示“整数”，实际写入的却是浮点成员。为什么即使两个成员大小相同，程序仍可能错误？

### 参考判断

空间大小只关系到存储能否容纳，标签决定读取时采用的语义。同一组位被当作另一种有效数据解释，会破坏协议。维护标签与有效载荷的一致性，是使用联合体必须承担的责任。

## 13. 作用域、链接与存储期：`static` 和 `extern` 到底控制什么

### 13.1 三个维度分别回答不同问题

| 维度 | 问题 | 不能误解成 |
| --- | --- | --- |
| 作用域 | 在源码哪些位置可以用这个名字 | 物理内存可以被谁访问 |
| 链接 | 不同声明是否指向同一个实体 | 对象位于 Flash 还是 RAM |
| 存储期 | 对象在执行过程中存在多久 | 名字在哪些文件可见 |

一个函数内的静态对象，名字只有块作用域，但对象可在多次调用之间持续存在。另一个文件级对象即使具有外部链接，也不表示它天然能被 DMA 访问：后者取决于存储器映射与硬件能力。

### 13.2 `static` 的三种常见用途

- 用于文件作用域对象，通常使其具有内部链接，其他翻译单元不能通过同一外部符号直接引用它。
- 用于文件作用域函数，使函数具有内部链接，表达模块内部实现。
- 用于块作用域对象，使该对象具有静态存储期，跨多次进入该块保留状态。

文件作用域对象本来就具有静态存储期，因此此处加入 `static` 的主要变化是链接属性。块内静态对象则解决“局部名字下保留状态”的问题，但所有调用仍可能共享这一份状态，影响可重入性。

`static` 不是内存访问控制机制。若内部对象地址被传给外部，外部仍可能通过合法指针访问它。封装来自接口设计，不能靠链接属性代替硬件保护。

### 13.3 `extern`、`auto` 与 `register` 的位置

`extern` 常用于引用已在别处定义的实体，不负责动态申请存储，也不表示对象由中断修改。它与前面可见声明的链接关系需要一致。

在 C11 / C17 中，`auto` 是自动存储期相关的存储类说明符，普通块内对象通常已有这种默认行为；它不是 C++ 式的通用类型推导。`register` 也不保证变量一定放在 CPU 寄存器中，在本文语言范围内还限制取地址。现代寄存器分配主要由编译器完成。

### 13.4 `static` 与 `extern` 的简例

```c
static unsigned int local_count = 0;
unsigned int shared_count = 0;

unsigned int next_count(void)
{
    static unsigned int calls = 0;
    return ++calls;
}
```

假定这些定义位于一个源文件：`local_count` 具有内部链接；`shared_count` 具有外部链接；`calls` 的名字只在函数块内可见，但对象跨调用持续存在。三个对象都有静态存储期，区别不在于其中两个是否“更长期”。

另一个源文件可以通过下面的声明引用共享对象：

```c
extern unsigned int shared_count;
```

这里没有提供第二个对象定义，最终程序仍需有兼容的定义。示例中的计数增量仅说明状态保留，不保证并发安全；无符号计数到达本类型上限后还会回绕。

### 推演检查

一个函数用局部 `static` 对象保存历史状态。两个独立实例轮流调用它，为什么状态可能相互影响？

### 参考判断

局部作用域只限制名字使用位置，不会为每次调用或每个设备生成独立的持久状态。两个实例共享了同一个对象。若希望实例独立，应让历史状态属于各自设备上下文。

## 14. `const`：只读约束为什么不等于“必定存放在 Flash”

### 14.1 先问“通过哪条访问路径能否修改”

`const` 用于限定类型，限制通过相应左值修改对象。接口中的只读访问可以表达“本操作只读取输入”，让编译器检查不应发生的写入，也让调用者理解约定。

指针本身与被指向对象是两个不同对象。指针值固定，表示不能借该名字改变指向；指向只读对象，表示不能经由该指针修改目标。两种约束可以分别存在，也可以同时存在。

### 14.2 只读视图不等于底层数据永远不变

一个原本可修改的对象，可以通过只读视图读取；其他合法的可写访问路径仍可能改变它。因此，指向只读数据不等于取得了永恒不变的快照，更不等于线程安全。

反过来，如果对象定义时就是 const 限定对象，再通过去掉限定的指针尝试修改，属于未定义行为。强制转换只改变表达式类型，不能推翻对象原有属性。

### 14.3 存放位置由实现与链接布局决定

字体表、查找表常被放进只读段并保留在 Flash 中，但这是编译器、链接脚本和存储架构共同实现的结果。函数内的 const 对象也可能与其他自动对象一样参与运行时计算。

在 C11 / C17 中，普通 const 整数对象并不自动成为语言要求的整数常量表达式。它与枚举常量、宏展开的常量表达式有区别。C23 的 `constexpr` 属于另一套规则，不能回套到旧工程。

### 14.4 三种指针限定的简例

```c
int value = 10;
const int *read_only = &value;
int * const fixed = &value;
const int * const fixed_read_only = &value;
```

| 名称 | 能否改为指向别处 | 能否通过它修改目标 |
| --- | --- | --- |
| `read_only` | 可以 | 不可以 |
| `fixed` | 不可以 | 可以 |
| `fixed_read_only` | 不可以 | 不可以 |

目标对象 `value` 本身没有被定义为 const，仍可通过合法的可写路径修改。因此只读指针既不冻结目标，也不产生副本。若目标本身就是 const 对象，去掉指针限定后强行写入仍属未定义行为。

### 推演检查

函数通过只读指针读取 DMA 接收缓冲区，能否因此断定读取期间内容不会变化？

### 参考判断

不能。只读约束限制该访问路径的写操作，不限制 DMA 或其他参与者。要获得稳定数据，需要所有权交接、双缓冲或其他同步协议；有缓存时还要处理一致性。

## 15. `volatile`：它为什么必要，又为什么经常不够

### 15.1 编译器为什么可能不重复读取一个普通对象

编译器会依据 C 程序中可见的修改关系进行优化。如果循环中的普通对象在它能够推断的执行范围内不变，它可能复用已读值。硬件寄存器、异步事件等变化，需要通过实现支持的方式进入编译器的行为约定。

`volatile` 限定用于表达相应访问具有必须被实现尊重的意义。具体哪些操作构成访问、如何对应机器访问，需要结合编译器和目标约定理解。它不是“这个变量完全禁止优化”的通用按钮。

对于 GCC，不能借 volatile 对象访问来推断周围普通内存已经被排序；volatile 本身不构成普通内存的发布屏障。[GCC 的 volatile 语义说明](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html)

### 15.2 把四种问题分开

| 需要保证的事情 | 单独使用 volatile 是否足够 |
| --- | --- |
| 对相应对象保留符合实现约定的访问 | 这是它关注的主要方向 |
| 一个多指令修改过程不可被打断 | 不够，需要原子操作或互斥等机制 |
| 普通数据先写完，再向其他执行者发布 | 不够，需要合适的同步与顺序保证 |
| CPU 缓存中的数据与 DMA 可见内存一致 | 不够，需要硬件一致性或缓存维护等措施 |

所以，“加上 volatile 后现象消失”可能只说明某一种优化暴露了问题，不能证明原子性、时序和一致性都已正确。

### 15.3 只读又可异步变化并不矛盾

一个硬件状态寄存器可以对软件只读，同时由外设自行改变。`const` 描述软件通过这条路径能否修改，`volatile` 描述访问的特殊性，两者回答不同问题。

中断不是 ISO C 线程模型对所有目标提供的统一机制。主循环和 ISR 共享状态时，需要遵循具体编译器的中断约定，再处理访问宽度、原子性和临界区，不能仅凭一个关键字推导整个系统。

### 15.4 `const volatile` 的简例

```c
unsigned int read_status(const volatile unsigned int *status)
{
    return *status;
}
```

`const` 限制通过这条访问路径写入，`volatile` 表达该次访问的特殊语义。两者可以同时存在，因为“软件不能通过它修改”与“值可能由其他机制改变”并不矛盾。

调用前仍需保证指针有效、目标范围和对齐正确。若用于 MMIO，还要由目标平台约定确保指针映射和访问宽度正确。这里的声明没有赋予访问原子性，也不会执行缓存维护或等待硬件完成。

### 推演检查

主循环和中断都对一个 volatile 计数器加一，为什么最终计数可能偏小？

### 参考判断

加一通常包含读取旧值、计算和写回。两方可能都基于同一旧值计算，后写回的一方覆盖另一方结果。保留每次访问并不能把整个读—修改—写过程变成不可分割操作。

## 16. `restrict` 与 `inline`：性能承诺为什么必须有成立条件

### 16.1 `restrict` 描述一段执行期间的访问关系

编译器面对多个指针时，需要考虑它们是否可能访问同一个对象。如果存在别名，某次写入可能使另一处读取的旧值失效，从而限制优化。

`restrict` 是程序员对相关指针访问关系作出的约束承诺。尤其当所访问对象在相应执行期间发生修改时，相关访问必须满足受限指针及其派生访问路径的规则。它并不是“这个地址在全程序中永远只允许出现一次”，纯读取重叠也不能被机械地一概判错。

可以用两种情形区分：两条输入路径只是读取同一片数据，并不必然违反这种约束；若通过一条受限路径修改某对象，又通过无关路径读取或修改该对象，就需要检查是否违反承诺。由原指针合法派生出的访问，与独立引入的另一条路径也应区分，不能仅计算程序中有几个指针变量。[WG14 N1570 第 6.7.3.1 节](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

违反这些约束不会保证产生运行时检查，而可能让编译器基于错误承诺生成不符合程序员直觉的结果。适合先建立清楚的缓冲区不重叠等接口前提，再考虑使用它；不能为了让函数看起来快而随意添加。

### 16.2 `inline` 不保证消除调用，也不保证缩小代码

内联替换可以减少调用开销，并让编译器结合调用点继续优化。但它也可能扩大机器码，增加取指压力。是否实际内联，取决于函数内容、优化设置和目标。

此外，`inline` 涉及 C 的定义与链接规则。GNU89、ISO C99 及其后续模式、C++ 的相关语义并不完全相同。尤其外部链接的内联函数，不能从某个工程的写法直接推导另一个模式下是否还需要外部定义。[GCC 内联函数说明](https://gcc.gnu.org/onlinedocs/gcc/Inline.html)

### 16.3 函数与宏的性能比较应建立在实际结果上

小函数具有类型检查和参数求值规则，编译器也可能自动内联。函数式宏只是预处理替换，不因为没有函数名调用就天然更快；重复求值甚至可能让外设访问发生多次。

### 16.4 为什么头文件中常把 `static` 与 `inline` 放在一起

两者分别处理不同问题：`static` 使函数具有内部链接，各翻译单元使用自己的函数实体；`inline` 涉及内联相关语义，编译器据条件决定是否展开调用。组合使用可以让头文件提供小型实现，而不产生多个同名的普通外部函数定义。

如果没有展开调用，实现仍可生成内部函数供本翻译单元调用；如果调用全部展开且无需独立函数实体，则可能不再生成单独机器码。因此，内联失败并不必然导致缺失实现，是否有额外代码占用仍需看构建结果。[GCC 内联函数说明](https://gcc.gnu.org/onlinedocs/gcc/Inline.html)

这种组织方式也有边界。函数里若保存可修改的局部静态状态，不同翻译单元的函数可能各自维护不同状态，不能把它当成全工程唯一服务。对外需要统一身份、集中维护状态的接口，通常应由一个实现文件承担明确的定义责任。

### 16.5 `restrict` 与 `inline` 的简例

```c
#include <stddef.h>

void copy_values(int *restrict dst, const int *restrict src, size_t count)
{
    for (size_t i = 0; i < count; ++i)
    {
        dst[i] = src[i];
    }
}
```

这个函数可以约定复制期间的源、目标访问区域不重叠，并且各自至少包含 count 个可访问元素。`restrict` 将访问约束告知编译器，但不会检查范围或重叠。若 count 为正且把同一有效区域同时作为源和目标，读取与写入路径不符合这里的受限访问承诺；不能仅因逐次赋值看起来无害就认定合法。

```c
static inline unsigned int smaller(unsigned int a, unsigned int b)
{
    return a < b ? a : b;
}
```

`static` 建立内部链接，`inline` 涉及内联语义。参数按函数调用规则传值，是否消除实际调用由编译器决定；两个关键字均没有赋予原子性或中断保护。

### 推演检查

复制函数原本只处理不重叠缓冲区，后来调用方传入重叠区域，并认为“算法方向正确就可以”。为什么仍需检查 restrict 约定？

### 参考判断

算法的逐步逻辑和语言层的访问承诺都必须成立。即使手工按某方向复制看起来可行，违反受限访问约定仍会破坏编译器可依赖的前提。需要重叠支持时，应选择具有相应语义的接口和实现。

## 17. 预处理与宏：为什么文本替换会影响类型和控制流

### 17.1 预处理发生在普通 C 类型检查之前

`#include`、`#define`、`#if`、`#ifdef`、`#ifndef`、`#elif`、`#else`、`#endif`、`#undef` 是预处理指令体系中的组成部分，不是普通运行时语句。宏展开产生的内容还要接受后续 C 语言分析。

条件编译适合选择芯片、板卡、功能组合，但运行时分支只能在已编译进程序的路径中选择。被条件编译排除的内容通常不会在当前构建中获得完整语义检查，所以配置越多，未经构建验证的路径也越多。

### 17.2 括号解决分组，不解决重复求值

函数式宏的参数可能在展开后出现多次。如果实参触发递增、读取 FIFO、读取后清零寄存器或进行通信，重复求值会改变行为。给参数加括号可以改善优先级问题，却不能减少出现次数。[GCC 关于宏副作用重复的说明](https://gcc.gnu.org/onlinedocs/cpp/Duplication-of-Side-Effects.html)

多语句宏还可能影响外部 `if` / `else` 的配对和分号使用。即使采用常见封装形式，也不能自动消除内部 `break`、`continue`、局部命名等带来的语义问题。

### 17.3 宏常量、枚举常量与 const 对象怎么区分

| 机制 | 核心性质 | 主要边界 |
| --- | --- | --- |
| 对象式宏 | 替换记号序列，可参与预处理选择 | 没有普通对象的作用域与独立类型约束 |
| 枚举常量 | 为整数语义命名 | 受对应语言版本的枚举规则约束 |
| const 对象 | 有类型的对象，可表达只读访问 | C11 / C17 中不自动成为整数常量表达式 |
| 小函数或内联函数 | 有函数接口和求值规则 | 实际是否内联由实现决定 |

编译器命令行中定义的宏同样会影响结果。排查“同一份源码行为不同”时，应比较最终配置和预处理结果，而不仅比较源文件文本。

### 推演检查

一个用于取较小值的宏，把读取接收 FIFO 的操作当作参数，为什么可能消费两个字节？

### 参考判断

宏展开可能先为比较读取一次，再为取得选中结果读取一次。FIFO 读取会改变硬件状态，两次读取不是同一值的重复观察。应先获取一次结果，再对稳定的值进行判断，或使用符合需求的函数接口。

## 18. 内存段与启动初始化：变量的初值怎样真正进入 RAM

### 18.1 语言中的对象，需要工具链安排物理存储

链接脚本通常描述 Flash、RAM 等区域，并将代码和数据段映射进去。段名是常见工具链组织习惯，并不是 C 标准要求芯片必须具有的结构。

| 常见区域 | 常见用途 | 需要理解的后果 |
| --- | --- | --- |
| `.text` | 指令代码 | 可执行地址、运行速度与存储器有关 |
| `.rodata` | 只读数据、查找表等 | 常在 Flash，但具体位置由布局决定 |
| `.data` | 具有非零等显式初始内容的可写静态数据 | 常需保存初值映像，再在启动时复制到 RAM |
| `.bss` | 采用零初始化表示的静态数据 | 常需启动时清零，通常不保存同尺寸的零字节映像 |
| 栈与分配区域 | 调用现场及动态分配对象等 | 实际组织由运行环境决定，不一定只有一块 |

编译器可以基于语义调整归类，例如显式初始化为零的对象仍可能放入 `.bss`。不能只通过源码是否写了初值判断最终段名。

### 18.2 装载地址与运行地址可能不同

可写初值保存在非易失存储中，但运行时对象位于 RAM，因此可能同时占用 Flash 映像空间与 RAM 运行空间。某些需要从 RAM 执行的函数也有类似的搬运过程。

CPU 复位后，RAM 里原本有什么内容，不等于 C 对静态对象初值的要求已经满足。启动过程负责把目标环境建立成语言和工程预期的状态。跳过启动初始化、从引导程序直接跳转，都必须重新检查这些前提。

### 18.3 保留区与多核启动需要额外协议

不初始化区域、掉电保留区域和核间共享区经常使用专用段或链接约定。旧数据被保留下来，并不意味着一定有效：需要版本、长度、校验或状态标记来判断。

两个核若都对同一共享区执行清零，后启动的一方可能破坏先启动的一方已经发布的内容。应该明确由谁初始化、何时完成以及另一方如何确认，而不是仅让双方声明相同变量。

### 推演检查

增加一个较大的带初值可写表格后，为什么 Flash 和 RAM 使用量可能同时增加？

### 参考判断

常见布局中，Flash 保存复位后要复制的初始内容，RAM 保存运行期间可修改的对象。这是两个不同用途的空间。若它实际不需要修改，应再评估只读属性与目标存储布局，但不能只改一个关键字就假定最终位置正确。

## 19. 栈与动态内存：可用空间为什么还不足以说明系统可靠

### 19.1 自动存储期不等于“所有局部变量都压栈”

自动存储期描述对象的生存期，栈是常见实现方式。编译器可能把对象保存在寄存器中，消除不需要的对象，或复用已经不再使用的存储。语言层不能直接推出每个名字的固定栈地址。

真实栈消耗可能包括局部数据、保存寄存器、函数调用现场、临时对象、运行库及异常现场。RTOS 常为任务提供独立栈，中断使用哪一块栈则由架构和端口决定，不能统一假定中断总使用独立栈。

最坏栈深度应沿最深可达调用路径考虑，还要叠加允许的中断嵌套、浮点上下文等开销。递归和变长数组会使上界更难分析；把大对象改为静态虽然减少栈压力，却会引入持久占用、共享及重入问题。

### 19.2 动态分配把空间选择推迟到运行时

`malloc`、`calloc`、`realloc`、`free` 是库接口，不是关键字。分配成功后形成有分配存储期的对象，释放后原对象不再有效。

动态分配的关键问题不只是总剩余空间：还包括连续块是否足够、分配时间是否可预测、失败怎样处理、谁拥有对象、何时释放、能否在当前上下文调用。RTOS 的专用分配器与 C 库分配器也可能使用不同区域、锁与统计信息。

对于有效的原分配对象和正的新尺寸，`realloc` 分配失败时原对象保持有效且内容不变；成功时应按返回的新对象关系使用，不能继续依赖原地址或内部旧指针。零尺寸的边界在不同语言版本中还有差异，接口设计宜明确避开或单独规定。

### 19.3 固定对象池用约束交换可预测性

固定大小对象池可简化分配和回收，便于控制最大对象数与时间上界，代价是尺寸不匹配可能浪费空间，容量需要预先规划。静态分配更容易确定峰值，但也不能替代所有权和并发管理。

### 推演检查

系统报告还有 8 KB 空闲内存，却分配不了 4 KB 缓冲区，这一定是统计错误吗？

### 参考判断

不一定。空闲空间可能分散为多个较小块，或者统计的区域与目标分配器实际使用的区域不同。还要考虑对齐、管理开销和内存能力限制。总空闲量不能直接证明存在足够大的合适连续块。

## 20. 生存期、别名与未定义行为：为什么“内存里还有值”不构成合法性证明

### 20.1 对象存在、已初始化和可访问，是不同条件

对象的生存期结束后，原指针不能继续作为有效访问依据。分配到存储也不代表已经写入可用值；自动对象若未完成必要初始化，直接使用不确定内容可能造成未定义行为或其他不可依赖的结果。

语言层的初始化按类型建立初值；逐字节写零只是在修改对象表示。不能把它推广为所有类型、所有平台上都等价于合法的零值或空指针初始化。`calloc` 保证的零字节填充也应按这一边界理解。

### 20.2 对齐正确仍可能违反访问类型规则

把一块内存转换为另一种指针，不会自动使里面存在对应类型的对象，也不会消除有效类型和别名规则的要求。某些类型组合允许访问，任意不相关类型则不能自由互换。

字符类型可用于查看对象表示，这是按字节处理的重要基础。但常见平台上的 `uint8_t` 往往是 `unsigned char` 的别名，不代表所有实现都必须如此。需要对象表示访问语义时，应知道依赖的究竟是字符类型规则还是平台别名约定。

字节复制可以避免某些不合法的类型化访问，但复制来的位模式仍需对目标类型有效。它也不自动处理网络字节序或通信协议解码。

### 20.3 三类不确定性要分开

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| 未定义行为 | 标准不再规定所讨论行为的结果 | 有符号溢出、越界访问、修改字符串字面量 |
| 实现定义行为 | 实现作出选择并说明 | 普通 char 的符号性、本文基线下某些整数转换 |
| 未指定行为 | 标准允许多个选择，不要求固定说明采用哪一个 | 没有依赖冲突时，某些实参的求值先后 |

未定义行为不要求立刻崩溃，也不等于“只是结果随机”。编译器可能依据合法程序不会走到某些情况的前提变换代码，所以错误可能表现为条件检查消失、不同优化级别行为不同，或在远离错误位置处暴露。

### 20.4 初始化建立对象值，赋值改变已有对象

初始化在对象形成时建立初值，后续赋值改变已有对象的值。具有静态存储期的对象在缺省情况下有语言规定的零初始化语义；未显式初始化的普通自动对象不能依赖存储中碰巧残留的值。

聚合对象有初始化器但只显式指定部分成员时，剩余成员按相应规则隐式初始化；这不同于先创建未初始化对象，再只给几个成员赋值。后一种情况下，其他成员不会因为相邻成员获得了值而自动完成初始化。

语言规定的初始化也不等于简单地把所有字节写成零。指针的空值、浮点零值和对象表示之间存在类型及实现条件，不能无条件用逐字节清零替代类型化初始化。

此外，具有确定值并不保证满足对象的逻辑约束。例如长度与容量都已经初始化，但长度大于容量，仍是无效的状态组合。应依次区分对象是否存在、值是否可用、成员间约束是否成立，以及当前是否允许访问。

### 推演检查

用一个整数指针读取接收缓冲区中的四个字节，只要地址对齐就肯定正确吗？

### 参考判断

还要判断存储范围、对象的有效类型与访问规则、字节序，以及这四个字节是否已由接收方完整发布。对齐只是其中一个前提。协议解析通常应先依据明确的字节规则构造数值。

## 21. 寄存器访问：为什么外设地址不能当普通变量使用

### 21.1 同样是读写，硬件可能把它解释为命令

MMIO 把外设寄存器映射到处理器可访问的地址空间。厂商通常用特定类型、结构体布局和 volatile 限定描述这些地址，但正确行为还依赖参考手册规定的访问宽度、权限和时序。

| 寄存器行为 | 访问的可能后果 |
| --- | --- |
| 普通读写 | 写入配置，随后读取当前状态或回读值 |
| 只读或只写 | 另一方向访问可能无意义、返回特殊值或不被允许 |
| 写 1 清零（W1C） | 写入的 1 用于清除对应状态，不是保存一个 1 |
| 读后清零或读出队 | 读取本身改变硬件状态 |
| 专用置位、清零寄存器 | 用单次特定写入修改目标位，避免软件读—修改—写 |
| 保留位、锁定和解锁字段 | 需遵循指定写法，不能任意覆盖 |

### 21.2 对 W1C 做普通读—修改—写为什么危险

假设两个待处理中断位当前都为 1，只想清除第一个。普通“读出原值，再合成写回”的方式可能把第二个位的 1 一起写回，结果第二个事件也被清掉。

危险不在位运算算错，而在“写入 1 的含义”与普通 RAM 不同。类似地，调试器持续刷新读后清零寄存器，也可能改变被观察系统。观察动作并非总是无副作用。

### 21.3 访问宽度、顺序与完成时刻各自独立

一个寄存器要求 32 位访问，就不能仅因只使用低字节而随意改为 8 位访问。一次 C 赋值也不能无条件推断为一种特定总线事务，必须结合实现、对齐及生成指令确认。

写操作已由 CPU 发出，不一定代表外设内部动作已经完成。某些配置需要屏障、回读、等待状态位或延迟，具体由芯片规定。通用的“每次写寄存器后都延时一下”既不能证明正确，也会掩盖真正的时序要求。

### 推演检查

调试时打开外设寄存器窗口后，接收数据似乎减少；关掉窗口现象消失。应考虑什么？

### 参考判断

调试器可能读取了有出队或清状态副作用的寄存器。需要确认调试器的读取行为及寄存器语义，避免把由观察动作引入的变化误判为应用逻辑错误。

## 22. 中断、原子性与同步：单核为什么也会出现并发错误

### 22.1 并发问题不要求真正同时执行

主循环在读取共享计数后被中断打断，中断更新计数，返回后主循环再写回旧值计算结果，就可能丢失更新。虽然任一瞬间只有一个执行者运行，操作仍在时间上交错。

区分三个层次很重要：一次机器访问是否不可分割，多个步骤组成的操作是否不可分割，以及多个字段是否构成一致快照。对齐的 32 位读取在某些 32 位平台上具备特定原子访问保证，也不等于整个计数增量或结构体复制具有同样保证。

在 C11 线程模型中，不同线程对同一内存位置发生冲突访问、至少一项非原子且缺少规定的先行关系，会形成数据竞争并导致未定义行为。因此不能把这种程序只理解为“偶尔读到旧值”。嵌入式 ISR 和 DMA 的具体契约仍需查平台，不能直接把它们等同于标准线程。[WG14 N1570 第 5.1.2.4 节](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

### 22.2 临界区必须覆盖真正的竞争者

单核中通过合适中断屏蔽保护短操作，可以排除被屏蔽的 ISR 竞争。进入和退出还要维护原有屏蔽状态，不能退出时一律开放本来已被关闭的中断。

中断屏蔽也有范围：可能只覆盖部分优先级，不阻止 DMA，不阻止另一个核。暂停任务调度通常仍允许中断执行。临界区实现还必须包含适当的编译器约束，防止应被保护的普通内存访问被移到区间外；只插入屏蔽指令的汇编文本未必表达了完整要求。临界区越长，最坏中断响应越差，应只覆盖保持一致性所需的最小操作。

### 22.3 `_Atomic` 解决什么，内存序又解决什么

C11 原子设施用于表达原子对象及操作。原子加载、原子存储与原子读—修改—写是不同操作；把“先原子读再原子写”拼起来，仍不能自动得到一个整体原子的更新。

内存序进一步约束操作之间的可见关系。`relaxed` 适用于只需要该原子操作自身保证的场合，不负责发布其他普通数据。典型发布过程是先写载荷，再以 release 语义发布状态；接收方以 acquire 语义读取到相应发布结果后，才建立所需同步关系。仅使用同名内存序而未读到对应发布，不能凭空建立关系。

原子设施是否受支持、某种类型是否无锁、会否调用运行库，都与目标有关。GCC 的原子内建在缺乏适合实现时可能产生外部调用，所以“原子”不等于“一条指令”或“必定适合 ISR”。[GCC 原子操作说明](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fatomic-Builtins.html)

### 22.4 可重入、线程安全与中断安全不是同义词

可重入强调一次调用未结束时再次进入能否正确工作。线程安全强调既定线程并发下正确；中断安全还受禁止阻塞、优先级和执行环境限制。

一个靠互斥锁实现线程安全的函数，若在 ISR 中等待被打断任务持有的锁，就可能永远等不到释放。多核自旋锁也必须考虑同核中断重入：如果 ISR 抢占了本核持锁代码后原地自旋，持锁者无法继续运行。

### 22.5 `_Atomic` 的简例：单个增量与数据发布不同

```c
#include <stdatomic.h>

static _Atomic unsigned int event_count = 0;

void count_event(void)
{
    atomic_fetch_add_explicit(&event_count, 1, memory_order_relaxed);
}
```

`_Atomic` 是关键字，`atomic_fetch_add_explicit` 是标准原子接口名称，`memory_order_relaxed` 是内存序名称。该操作将取旧值与加一作为原子读—修改—写完成；在其他访问也遵循原子规则时，不会发生普通读改写那样的增量覆盖，但计数值仍有范围上限和回绕语义。

这里没有发布另一块普通载荷的同步关系，也没有证明目标实现无锁或可在 ISR 中使用。原子对象、所选操作与内存序各自承担不同责任。

### 推演检查

主循环复制两个共享字段时屏蔽了普通中断，却仍读到不匹配的数据，可能遗漏了什么？

### 参考判断

写入者可能是未被屏蔽的高优先级 ISR、DMA 或另一核心，也可能复制前后使用了失效的状态判断。保护范围必须覆盖真实写入者与完整一致性区间，不能只确认“已经调用了临界区入口”。

## 23. DMA、缓存与多核：数据已经写完，另一方为什么还看不到

### 23.1 先分开可达性、可见性与所有权

DMA 能否访问某个 RAM 区域，是总线与存储器映射问题；CPU 读到的是否为最新数据，是缓存与同步问题；谁在当前阶段可以修改缓冲区，是软件所有权问题。这三项相互影响，却不能互相替代。

两个核看到相同的地址数值，也不自动表示访问同一物理存储。系统还可能存在本地地址映射、私有存储及不同内存属性。建立共享协议之前，应先确认共享区域对各参与方的实际映射和能力。

### 23.2 有缓存时，CPU 与 DMA 可能面对不同副本

在非硬件一致的系统中，CPU 写入数据可能先停留在脏缓存行，DMA 从 RAM 读到旧内容。反过来，DMA 已更新 RAM，CPU 仍可能命中自己的旧缓存行。

- Clean：使缓存中的脏数据按平台要求写回相关内存层级。
- Invalidate：使相关缓存副本失效，后续读取重新取得数据。
- 屏障：对特定访问的顺序或完成提供架构规定的约束，不能代替必要的数据写回或失效。

缓存维护以缓存行为粒度。CMSIS 的相关 D-Cache 按地址操作也明确规定了地址对齐要求；具体平台的行大小和 API 要求应查对应文档，不能把一个内核的数值推广到所有芯片。[CMSIS D-Cache 文档](https://arm-software.github.io/CMSIS_6/main/Core/group__Dcache__functions__m7.html)

### 23.3 发送与接收的风险方向不同

CPU 准备数据交给 DMA 读取时，通常需要先完成载荷，再按平台要求写回相关缓存并保证必要顺序，最后交出所有权。DMA 持有期间，CPU 不应继续修改正在发送的区域。

DMA 写入、CPU 随后读取时，则需避免旧的脏缓存行在传输期间或之后写回并覆盖新数据，也需避免 CPU 继续读取旧缓存。移交前的维护、完成后的失效和屏障顺序必须按平台方案执行，不能概括为“结束后随便清一次缓存”。

如果接收区与无关可写对象共享缓存行，失效可能丢掉邻接对象的脏数据，写回也可能影响 DMA 区域。独立且满足缓存行边界要求的缓冲区，更容易建立正确的所有权协议。

### 23.4 多核发布必须是一条完整链路

典型过程是：**准备载荷 → 满足缓存与顺序要求 → 发布完成状态或通知 → 接收方建立对应同步 → 读取载荷 → 归还所有权**。

硬件信号量可能提供互斥能力，却不当然承担所有缓存维护。普通通知也不当然发布此前全部写入。原子对象和标准内存序主要描述适用执行环境中的 CPU 访问关系，DMA 等外部代理需要额外遵循平台规则。

单生产者、单消费者环形缓冲区可以通过各自拥有的索引减少竞争，但仍需保证先写数据再发布可读位置、读完后才发布可复用空间。加入第二个生产者后，原有“一人写一个索引”的证明就不再成立。

### 推演检查

DMA 完成标志已出现，CPU 看到的接收内容却仍是上一帧；把缓冲区加上 volatile 后偶尔正常。应如何解释？

### 参考判断

标志只能证明某个完成事件，不能独立证明 CPU 缓存已更新、缓冲区归属正确或下一次 DMA 尚未覆盖。volatile 不会自动使旧缓存行失效。应逐项检查地址可达性、内存属性、缓存维护、通知顺序和缓冲区复用时机。

## 24. 接口、错误与模块：怎样让调用者知道哪些事被保证

### 24.1 函数类型只表达接口的一部分

一个整数参数可能表示频率、周期、计数值或百分比；单靠类型未必能区分。完整接口需要描述单位、允许范围、边界行为、对象生存期、所有权、并发限制和时间特性。

异步发送接口尤其需要回答：返回时只是提交成功，还是已经发完？发送期间谁持有缓冲区？失败时硬件可能完成了多少？完成回调在哪种上下文执行？这些问题直接决定上层能否安全复用对象。

### 24.2 错误路径也应具有可解释的状态

失败不总意味着系统回到了调用前。配置外设可能已经改动一部分寄存器，通信可能已经发送部分数据，分配操作可能已经取得一部分资源。

应明确失败后的状态：保持原状态、进入可恢复状态，还是需要重新初始化。错误码如果只被底层打印后丢弃，上层就无法选择重试、降级或停止。重复操作是否安全，也需要结合幂等性和外设副作用判断。

### 24.3 分层隔离的是变化与责任

| 层次 | 主要负责 | 不宜混入的内容 |
| --- | --- | --- |
| 平台访问层 | 内核、寄存器、底层同步与平台限制 | 应用业务决策 |
| BSP / 设备层 | 板级连接、设备能力与操作接口 | 与某个应用流程紧耦合的状态 |
| 服务与任务层 | 缓冲、调度、事件、设备协作 | 任意绕过设备层修改内部寄存器 |
| 应用层 | 工作模式、状态机和业务策略 | 依赖内部变量布局的越层访问 |

模块私有状态与公开操作结合，能缩小错误来源。需要支持多个实例时，应把设备状态与行为分离，让每个实例拥有自己的上下文，而不是逐个增加全局变量。

### 推演检查

一个异步接口返回成功后，调用者立即修改输入缓冲区。为什么操作结果可能同时包含修改前后的内容？

### 参考判断

明确成功表示“已接收请求”还是“传输完成”，以及缓冲区何时归还调用者。如果只是启动 DMA，成功返回不代表外设已经读完。接口要么完成必要复制，要么要求调用者在完成通知前保持数据有效且不变。

## 25. 编译优化与诊断：为什么关闭优化只能帮助定位，不能证明修复

### 25.1 编译器维护的是语言语义，不是逐行执行的外观

优化可能消除无用存储、合并计算、展开循环、内联函数或改变指令组织。合法变换需要保持所要求的可观察行为，但源代码行与机器指令不必一一对应。

所以调试器显示对象被优化掉、单步顺序不直观，不一定表示程序错误。另一方面，未定义行为、未表达的异步访问或错误别名承诺，会让优化暴露原本已存在的问题。

不同优化等级包含的具体策略与目标、版本有关，不能把某个等级理解为固定指令变换清单。提高优化也可能影响代码大小、调试体验及实际运行时间，需在目标上验证。[GCC 优化选项说明](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html)

### 25.2 警告用于发现假设，不能只靠转换把它压下去

窄化、符号转换、遮蔽同名变量、格式不匹配、未定义预处理标识符和不完整原型等警告，经常指向接口或范围假设不清。

正确处理顺序是先解释为什么产生警告，再决定是改类型、改接口、补检查，还是用经过证明的显式转换表达意图。强制转换消除了诊断，不代表修复了范围或生存期问题。

对自有应用与 BSP 可以设置更严格的诊断标准，同时保留第三方代码的维护边界。不能为了得到零警告而大范围修改不了解的供应商实现。

### 25.3 不同证据回答不同问题

| 证据 | 可以帮助确认 | 不能单独证明 |
| --- | --- | --- |
| 编译器诊断 | 一部分类型、控制流和使用问题 | 没有运行时越界或并发错误 |
| map 文件 | 符号、段和地址布局 | 运行时最大栈深度和时序正确 |
| 反汇编 | 实际指令、访问宽度、调用和屏障 | 所有可能输入下的协议正确 |
| 栈水位与运行统计 | 已覆盖执行路径的资源使用 | 未运行路径的最坏上界 |
| 单元验证与上板观察 | 特定条件下的行为与边界 | 任意平台与任意并发交错都正确 |

### 推演检查

某轮询程序只有关闭优化才工作，应立即把所有变量都改成 volatile 吗？

### 参考判断

应先确定等待对象由谁改变、声明是否正确、是否存在越界或其他未定义行为，再检查同步协议与生成指令。大面积增加 volatile 会改变现象，却可能留下真正的并发或内存问题。

## 26. 编译期约束与平台扩展：怎样把隐含前提变成明确规则

### 26.1 有些条件适合在构建时就拒绝

`_Static_assert` 用于检查编译期条件，例如类型大小或布局要求是否满足。它不执行运行时输入验证，但可以避免在目标配置已经不满足前提时继续生成程序。

`_Alignas` 表达对齐要求，`_Alignof` 查询类型对齐需求。更强对齐不会自动把对象放到 DMA 可达区域，也不会自动获得缓存一致性。`_Generic` 按类型选择表达式，适合在语言允许的范围内构建类型相关接口；它不是运行时动态类型检查。

`_Noreturn` 表达函数不会正常返回调用者的契约，例如某些终止或不可恢复处理。它不表示函数不会阻塞，也不表示中断会被禁止；一旦错误地正常返回，就破坏了编译器可依赖的前提。

### 26.2 线程局部对象需要运行环境配合

`_Thread_local` 表达线程存储期，每个线程拥有相应实例。但“线程”如何与具体 RTOS 任务对应，取决于编译器 ABI、运行库及 RTOS 集成。

不能仅因关键字编译通过，就认定每个任务都有独立对象。裸机或精简运行库可能不提供所需支持；ISR 访问线程局部对象还需明确它看到的是哪个执行上下文。

### 26.3 常见厂商标记多数不是标准 C 关键字

| 常见名称或类别 | 通常表达的意图 | 必须继续检查的条件 |
| --- | --- | --- |
| `__IO`、`__I`、`__O` 等 | 封装访问限定或厂商约定 | 以实际头文件展开内容为准，名字不等于硬件权限 |
| `__weak` / weak 属性 | 提供可被其他定义替换的默认实现 | 符号、链接输入、静态库抽取和覆盖规则 |
| packed、aligned | 调整布局或对齐 | 成员访问、ABI、链接器支持 |
| section | 指定输入段归属 | 链接脚本是否把该段放到合适区域 |
| used、retain、链接脚本 KEEP | 在不同阶段影响保留 | 编译器发出符号与链接器保留段不是同一件事 |
| `asm`、`__asm`、`__attribute__` | 编译器扩展入口 | 约束、破坏项、目标架构和编译模式 |
| interrupt 等目标属性 | 建立目标要求的中断调用约定 | 保存现场、返回指令、向量绑定等平台条件 |

例如，GCC 的 used 主要涉及让编译器保留并发出相应实体；在启用链接垃圾回收时，还要检查链接阶段的保留方式。GNU ld 的 KEEP 用于保护指定输入段免于相应回收。[GNU ld 对 KEEP 的说明](https://sourceware.org/binutils/docs/ld/Input-Section-Keep.html)

自定义向量表、注册表和仅由硬件引用的描述符尤其需要检查最终映像。源文件中存在一个对象，不代表它一定到达最终烧录文件。

### 26.4 `_Static_assert`、`_Alignas` 与 `_Alignof` 的简例

```c
#include <limits.h>

_Static_assert(CHAR_BIT == 8, "requires 8-bit bytes");
_Alignas(unsigned long) unsigned char storage[64];
_Static_assert(sizeof storage >= sizeof(unsigned long), "insufficient capacity");
```

第一条断言把字节位数要求变成构建条件；`_Alignas` 要求 storage 至少满足 unsigned long 的对齐；第二条断言检查容量前提。`_Alignof(unsigned long)` 则可以查询该类型的对齐需求。

这几项共同说明了“字节位数、空间容量、地址对齐”三个独立条件，但没有把字符数组变成 unsigned long 对象，也没有改变别名规则、DMA 可达性或缓存属性。编译期检查只能证明所写出的条件。

### 推演检查

为 DMA 缓冲区指定专用段后，它仍无法传输，是否说明 section 属性无效？

### 参考判断

不一定。指定段只表达归类，实际地址仍由链接规则决定。还要检查段是否保留、运行地址是否可达、对齐和缓存属性是否正确，以及缓冲区是否在 DMA 完成前持续有效。应从最终映像和地址映射核实，而非只看声明。

| 预处理指令 | `#include`、`#define`、`#if`、`#pragma` | 控制预处理或实现行为，不是运行时函数 |
| 厂商与编译器标记 | `__IO`、`__weak`、`__packed`、`__asm` | 需要查看当前工具链与头文件定义 |

`offsetof` 可用于合适结构体成员的偏移查询，但不是对位域的通用偏移工具。`assert` 通常用于运行时开发检查，还可能在特定配置下被移除，因此不能让它承担必需的状态更新或输入处理。

## 附录 B：遇到实际问题时，应该选择哪类机制

| 实际需求 | 首先考虑 | 不能替代它的东西 |
| --- | --- | --- |
| 只在模块内部暴露名字 | 内部链接、私有状态与公开接口 | 仅靠命名约定 |
| 多次调用之间保留状态 | 明确存储期与实例归属 | 无条件增加全局变量 |
| 表达只读输入 | 合适的 const 限定 | 假定数据永远不变 |
| 按实现约定访问硬件状态 | 正确的 volatile 限定和 MMIO 定义 | 对所有变量一律加 volatile |
| 保证计数增量不丢失 | 原子读—修改—写或适当临界区 | 分开的原子读和原子写 |
| 发布普通内存中的完整载荷 | 对应同步、所有权与必要内存序 | 单个普通或 volatile 标志 |
| 让 DMA 读取 CPU 新数据 | 可达区域、必要缓存维护与交接 | const 或 volatile |
| 让 CPU 读取 DMA 新数据 | 完成确认、正确失效策略与所有权 | 只观察到 DMA 完成标志 |
| 建立固定通信格式 | 显式字段编码与解码 | 直接发送任意结构体内存 |
| 限制资源上界 | 静态规划、对象池、明确生命周期 | 只统计总空闲内存 |
| 提前发现平台假设不成立 | 编译期约束与构建验证 | 只在注释中写“应当如此” |
| 确保硬件引用对象留在映像 | 编译与链接保留规则、映像检查 | 仅看到源码中存在定义 |

## 附录 C：跨章节概念推演

### 场景一：结果类型足够宽，为什么表达式仍可能溢出

**已知条件：** 两个窄整数先相乘，结果最后存入宽整数对象。

**推演顺序：**

1. 根据整数提升规则，确定乘法的实际操作数类型。
2. 根据通常算术转换，确定结果表达式的类型。
3. 用操作数允许范围推导最大乘积，判断该类型是否可表示。
4. 确定向目标宽类型的转换是在乘法之前还是之后。
5. 区分有符号溢出、无符号回绕和赋值窄化各自的语义。

**参考判断：** 接收结果的类型不会追溯改变此前的计算类型。每一步都应在其实际类型下成立，最终结果能够表示并不足以证明中间运算合法。

### 场景二：一段连续内存为什么不能随意按任意类型读取

**已知条件：** 一块存储区域的字节数足够，地址也满足目标整数类型的对齐。

**推演顺序：**

1. 确认其中存在什么对象，对象是否仍在生存期内。
2. 确认访问范围没有超出对象边界。
3. 检查所用类型是否满足有效类型与别名规则。
4. 判断对象表示是否对目标解释有效，是否涉及字节序。
5. 若存在其他执行者，确认内容已经完整发布且读取期间不会失效。

**参考判断：** 地址和大小是访问条件的一部分。对齐不会建立对象生存期，类型转换不会授予任意别名访问权限，同一组字节也不天然具有同一个数值含义。

### 场景三：单次访问原子，为什么整体状态仍不一致

**已知条件：** 两个字段的单次读取和写入均满足目标平台的原子访问条件，但两个字段要共同表达一个状态。

**推演顺序：**

1. 列出每个对象的所有读者与写者，标明任务、ISR 和其他硬件代理。
2. 区分单次访问、复合更新、跨字段快照三个原子性层次。
3. 确认所用保护是否覆盖真实写者及所需完整区间。
4. 检查中断屏蔽状态是否正确恢复，是否引入过长延迟或锁重入。
5. 如果采用原子对象，确认目标实现和内存序契约。

**参考判断：** 不同字段各自原子，不代表组合快照原子。应选择合适的短临界区、版本化快照或消息传递等设计，并证明其所有读写都遵循同一协议。

### 场景四：对象仍然存在，为什么异步访问仍可能失效

**已知条件：** 接口保存了缓冲区地址，返回后仍在读取它；调用者则准备再次使用同一块存储。

**推演顺序：**

1. 确认成功是提交成功还是完成成功。
2. 确认缓冲区是自动对象、静态对象还是动态对象，生存期是否覆盖传输。
3. 判断调用者在完成前是否覆盖了同一存储。
4. 如果涉及缓存，检查 DMA 所见内容与 CPU 最后写入是否一致。
5. 为每次提交、完成、失败和取消定义所有权转移。

**参考判断：** 地址仍有效与内容仍稳定是两种要求。把局部缓冲区改为静态只可能解决生存期，仍可能被下一次调用覆盖；独立缓冲、复制或等待完成需要按吞吐与内存预算选择。

### 场景五：源码先写数据再置位，为什么不等于完成发布

**已知条件：** 两个执行者使用共享载荷和就绪标志，但尚未建立明确的同步、缓存与所有权规则。

**推演顺序：**

1. 验证两个核映射到同一共享物理内存，且区域属性合适。
2. 检查有无硬件缓存一致性；没有时明确维护责任。
3. 确认发布、接收之间建立了实际同步关系，而不是只有源码先后顺序。
4. 检查生产者是否在消费者读完前开始覆盖下一包。
5. 检查完成通知是否可能合并、丢失或无法区分不同消息代次。

**参考判断：** 单一就绪位不一定足以描述多次传输。可使用有明确容量、序号和归还规则的协议。内存序不能替代容量管理，信号量不能自动代替缓存维护。

### 场景六：源文件中有定义，为什么最终映像可能没有对应对象

**已知条件：** 一个对象只通过硬件或约定地址被引用，普通 C 调用关系中没有可见的引用路径。

**推演顺序：**

1. 从最终 ELF / map 确认对象是否存在，地址和对齐是否正确。
2. 检查编译器是否发出实体，链接器是否将相关段回收。
3. 检查弱定义覆盖、静态库抽取和链接脚本选择规则。
4. 检查硬件或框架引用的是最终正确地址，函数调用约定是否匹配。
5. 再检查所需启动初始化和平台扩展是否实际生效。

**参考判断：** “源文件中写了”只证明文本存在，不能证明最终系统存在相应对象。定位需要跨越源码、目标文件、链接映像与启动运行四个阶段。

## 附录 E：语言版本与平台边界

### E.1 本文基线与 C23 的差异

本文正文按 C11 / C17 推理。C23 增加或调整了若干语言能力，识别它们有助于阅读新资料，但应以项目实际启用模式和编译器支持为准。

| 项目 | 本文 C11 / C17 基线 | C23 阅读时需要更新的认识 |
| --- | --- | --- |
| 布尔名称 | `_Bool` 是关键字；标准头文件提供 bool、true、false 宏 | bool、true、false 成为关键字 |
| 对齐、静态断言、线程局部名称 | 使用相应下划线关键字，部分标准头文件提供便利宏 | 增加 alignas、alignof、static_assert、thread_local 关键字拼写 |
| 空指针表达 | 按空指针常量和 NULL 规则理解 | 引入 nullptr 及相关类型支持 |
| 常量对象与类型推导 | 普通 const 不等于整数常量表达式；auto 不用于该类推导 | 引入 constexpr，并扩展 auto 的推导用途 |
| 空参数列表 | 旧式空列表声明不提供完整原型参数信息 | 相关规则改变，不再沿用旧的未指定参数含义 |
| 整数与枚举 | 本文按旧版转换与枚举规则限定结论 | 有符号表示、转换、枚举等存在更新，应查对应条款 |

上表是辨析入口，不是完整 C23 变化清单；正式使用新特性前，应核对标准、编译器版本与目标运行库。[WG14 C23 工作草案 N3096](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n3096.pdf)

### E.2 跨 MCU 迁移时不能继承的默认假设

- 数据模型：整数、指针、枚举宽度，char 符号性，浮点能力和字节序。
- ABI：对齐、调用约定、中断入口、结构体传参与运行库兼容性。
- 内存：区域容量与可达性，栈组织，缓存属性和 DMA 限制。
- 并发：中断优先级与屏蔽范围，原子操作支持，多核互斥和一致性机制。
- 工具链：扩展关键字、弱符号、内联语义、链接脚本及保留规则。

不同 MCU 可以复用许多 C 层规则，但一个架构的中断屏蔽、缓存屏障或原子访问保证，不能未经核实就原样迁移到另一个架构。

### E.3 标识符命名也有标准边界

双下划线开头，或下划线后紧跟大写字母的标识符，属于应留给实现使用的范围；文件作用域的下划线开头标识符还受相应保留规则约束。标准库也保留一些特定名称和用途。

因此，厂商头文件采用某种名字，不代表用户模块可以照搬同样前缀。理解扩展名称即可，不应把实现保留形式当作个人代码的通用命名习惯。
